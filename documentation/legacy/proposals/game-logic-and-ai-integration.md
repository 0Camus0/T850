## Design Principles

1. **Core framework feature** — shipped as part of the T850 framework, built via MSBuild (`.vcxproj`). Always available.
2. **Non-intrusive** — no changes to core rendering, physics, or navmesh systems. All new code lives in a new `game/` module.
3. **Generic** — designed to work for RTS, FPS, RPG, tower defense, or any genre that needs entity behavior.
4. **Composable** — small, independent systems that layer on top of each other. Users enable only what they need at runtime.
5. **Editor-friendly** — ImGui panels for visualization, inspection, and debugging. Scene file (`.t8scene`) extension for authoring.

## Implementation-Ready Contract

This section supersedes broader example code later in this proposal when there is a conflict. It is written for direct implementation in the current T850 source tree by a small, lightweight coding model.

### Current Source Reality

- `Framework/include/scene/EditorSceneFile.h` already contains `SceneGameEntityDesc` and top-level `EditorSceneFile::game_entities`.
- Current `SceneGameEntityDesc` is relationship metadata only: name, kind, mesh link, physics links, camera, ragdoll, legacy `ai`, visibility, frozen, and wire flags.
- T8ditor already owns `EditorWorld::gameEntities`, saves it in `BuildEditorSceneSnapshot()`, restores it in `ApplyEditorUndoState()`, and displays a basic Game Entities hierarchy section.
- `DayScene/SceneTemplate.cpp` currently loads objects, physics, navigation, splines, cameras, lights, profiles, God Rays, and ragdolls. It does not yet instantiate runtime gameplay objects from `scene.game_entities`.
- There is no current `Framework/include/game` or `Framework/src/game` module.

Therefore the first milestone is not "add every gameplay feature." The first milestone is: make existing `game_entities` meaningful at runtime.

### C++ And Dependency Rules

The MSBuild projects currently use C++23 (`stdcpp23`). The implementation may use:

- `std::unique_ptr` for component ownership.
- `std::optional` for optional scene/runtime data.
- `std::string_view` for non-owning type names and event names.
- `std::span` for read-only batch views where lifetime is obvious.
- `std::unordered_map` for ID lookup tables.
- `std::deque` or a vector-backed ring buffer for event logs.
- `std::mutex` and `std::atomic` only at explicit cross-thread boundaries.

Do not introduce a third-party ECS, reflection, scripting, or UUID dependency in the first slice. Stable IDs are serialized as strings generated by a small T850 helper.

### Stable Identity

Gameplay references must use stable serialized IDs, not display names or editor vector indices.

```cpp
namespace t850::game {
  using RuntimeGameObjectId = uint32_t;
  constexpr RuntimeGameObjectId kInvalidRuntimeGameObjectId = 0;

  std::string MakeStableId(std::string_view prefix); // e.g. "ge_...", "comp_..."
}
```

ID rules:

- Generate IDs in T8ditor when creating game entities, components, and later groups.
- Preserve IDs on rename, save, load, undo, and redo.
- Duplicate/copy creates new IDs for the copied entity and copied components.
- Old scenes with missing IDs are migrated by `MigrateEditorSceneGameLogic()`.
- Runtime IDs are allocated on load and are never serialized.

### Runtime Ownership

For the first implementation, `GameLogicSystem` is owned by `SceneTemplate`, not `EngineContext` and not a global singleton.

```cpp
class SceneTemplate : public SceneBase {
  ...
  t850::game::GameLogicSystem m_gameLogic;
};
```

Load order:

```text
SceneTemplate::LoadEditorSceneAssets(scenePath)
  1. Load EditorSceneFile.
  2. Load render objects into PrimitiveInst slots.
  3. Load physics, navigation, cameras, lights, splines, ragdolls.
  4. Build GameSceneRuntimeLinks from loaded object names, physics entity names, cameras, ragdolls.
  5. Validate/migrate game-logic data.
  6. m_gameLogic.LoadFromScene(scene, links).
```

### Fixed Tick And Phase Order

Gameplay uses a fixed tick even when rendering uses variable timestep.

```cpp
struct GameLogicSettings {
  float fixedDeltaSeconds = 1.0f / 60.0f;
  float maxFrameDeltaSeconds = 0.25f;
  int maxStepsPerFrame = 4;
};
```

`GameLogicSystem::Update(float deltaSeconds)` accumulates time and calls `Tick(fixedDeltaSeconds)` at most `maxStepsPerFrame` times.

Tick phase order:

```text
Tick(dt)
  1. BeginTelemetry
  2. ApplyDeferredEntityCreates
  3. DispatchQueuedEventsFromPreviousTick
  4. UpdateComponents(PrePhysics)
  5. FlushPhysicsCommands
  6. UpdateComponents(PostPhysics)
  7. ResolveNavigationResults
  8. UpdateComponents(Logic)
  9. EvaluateStateMachines
 10. UpdateGroupsAndExampleSystems
 11. UpdateComponents(Late)
 12. ApplyDeferredEntityDestroys
 13. EndTelemetry
```

Several phases can be empty in slice 0. They still exist so future code has a safe destination.

### Thread Safety Model

Default rule: `GameLogicSystem::Tick()` and all component callbacks run on the main scene thread.

Allowed worker-thread work:

- read-only path requests that copy inputs and return results through a completion queue;
- read-only expensive spatial batches after the registry has produced an immutable snapshot;
- asset/config loading through `ResourceLocator` before runtime object mutation.

Forbidden in worker callbacks:

- mutating `GameObjectRegistry`;
- mutating `PrimitiveInst`, `RenderMesh`, `RenderSkinnedMesh`, `AnimationController`, or T8ditor state;
- publishing immediate events into active dispatch;
- destroying entities/components;
- calling Jolt/Detour APIs that are not documented as thread-safe for that use.

Cross-thread handoff uses owned data copied into command/result queues. Protect queues with `std::mutex` unless a measured bottleneck justifies a lock-free structure.

Physics writes are command-buffered and flushed in the fixed tick phase. Components do not directly mutate Jolt bodies from arbitrary callbacks.

### First Vertical Slice

Slice 0 deliverable:

1. Extend `SceneGameEntityDesc` with `id` and `components` only.
2. Add `SceneComponentDesc` with `id`, `type`, `enabled`, `params`, and `config_json`.
3. Add validation/migration for IDs and broken mesh/physics references.
4. Add `GameLogicSystem`, `GameObjectRegistry`, `Component`, and `ComponentFactory`.
5. SceneTemplate loads `scene.game_entities` into runtime `GameObject` records and links mesh/physics/camera/ragdoll references.
6. Add a DevGui panel showing runtime game objects and resolved links.
7. Shut down and reload cleanly.

Out of scope for slice 0: groups, formations, flocking, combat, resources, visual state graph, hot reload, full ECS.

## Shared Framework Architecture

### Core Principle: No Duplication

The T850 framework already establishes a pattern where **scene schema types live in the Framework layer** and are shared between T8ditor (editor) and runtime applications (SceneTemplate, custom games). The `EditorSceneFile.h` header at `Framework/include/scene/EditorSceneFile.h` defines `SceneGameEntityDesc`, `SceneObjectDesc`, `SceneCameraDesc`, `SceneLightDesc`, `ScenePhysicsCharacterDesc`, and all other scene authoring types — in the `t850::scene` namespace.

**Game logic scene types follow this same pattern.** Component descriptors, state machine definitions, and group configurations are added to the Framework scene schema layer, NOT to the editor. The editor then consumes these shared types for UI, selection, save/load, and undo.

| Concern | Framework Responsibility | Editor Responsibility |

## Layer 1: GameObject & Components

### GameObject

A lightweight runtime record that links authored game entities to loaded SceneTemplate resources. It does not own render meshes, physics bodies, cameras, or ragdolls; it stores links to them.

```cpp
namespace t850::game {

struct GameObjectLinks {
  int meshSlot = -1;
  t850::PrimitiveInst* primitive = nullptr;
  std::string meshObjectName;
  std::string primaryPhysicsEntityName;
  std::vector<std::string> physicsEntityNames;
  int cameraIndex = -1;
  int ragdollIndex = -1;
};

struct GameObject {
  RuntimeGameObjectId runtimeId = kInvalidRuntimeGameObjectId;
  std::string sceneId;        // Serialized stable SceneGameEntityDesc::id.
  std::string name;           // Display name.
  std::string kind = "generic";
  bool enabled = true;
  GameObjectLinks links;
  std::vector<std::unique_ptr<Component>> components;
};

} // namespace t850::game
```

## Layer 2: State Machine Framework

### State Machine

Each `GameObject` can have an attached `StateMachine` component:

```cpp
class State {
public:
    virtual ~State() = default;
    virtual std::string_view Name() const = 0;
    virtual void OnEnter(GameObject& owner) = 0;
    virtual std::optional<std::string> Update(GameObject& owner, float dt) = 0; // Returns next state name, or nullopt
    virtual void OnExit(GameObject& owner) = 0;
};

class StateMachine {
public:
    void AddState(std::unique_ptr<State> state);
    void SetInitialState(const std::string& name);
    void Update(GameObject& owner, float dt);  // Handles transitions
    std::string CurrentStateName() const;

private:
    std::unordered_map<std::string, std::unique_ptr<State>> states_;
    std::string currentStateName_;
    State* currentState_ = nullptr;
};
```

### Transition Rules

Transitions can be explicit (state returns next state name) or rule-based:

```cpp
struct TransitionRule {
    std::string fromState;
    std::string toState;
    std::function<bool(GameObject&)> condition;
    float cooldown = 0.0f;          // Min time between transitions
    float elapsedCooldown = 0.0f;
};

// Example:
sm.AddTransition("Idle", "Attack", [](GameObject& g) {
    auto* sensor = g.GetComponent<SensorComponent>();
    return sensor && !sensor->DetectedEnemies().empty();
});
```

### Pre-built States

| State | Description | Exit Condition |
|---|---|---|
| `IdleState` | Wait, patrol waypoints, or hover in place | Enemy detected, move command received |
| `MoveToState` | Navigate to world position via navmesh | Arrived at target, blocked, or interrupted |
| `AttackState` | Face target, attack in range, chase if out of range | Target dead, lost LOS, or retreat ordered |
| `HarvestState` | Move to resource → collect → return to base → deposit | Resource depleted, unit destroyed |
| `BuildState` | Move to build site → play construction animation → spawn building | Build complete, interrupted by attack |
| `FleeState` | Run away from nearest threat, seek cover | Threat gone, health critical (different behavior) |
| `DefendState` | Hold position, engage any threat in detection radius | Position lost, retreat ordered |
| `RepairState` | Move to allied unit/building, play repair animation | Target at full HP, unit reassigned |

### Integration Points

- **`MoveToState`** → uses `NavigationWorld::FindPath()` + Detour path following
- **`AttackState`** → uses `JoltPhysicsSystem` sweep for line-of-sight validation
- **All states** → transition `AnimationController` to matching animation clips (e.g., `AttackState` → attack anim)
- **Character movement** → drives `KinematicCharacterController` velocity input

## Layer 4: Event/Message Bus

Events are queued per fixed tick. Immediate recursive dispatch is not allowed in the first implementation because it makes entity destruction and state transitions hard to reason about.

```cpp
struct GameEvent {
  uint64_t sequence = 0;
  uint64_t tick = 0;
  std::string type;
  std::string sourceEntityId;
  std::string targetEntityId;
  std::map<std::string, std::string> params;
};

class EventBus {
public:
  using Handler = std::function<void(const GameEvent&)>;

  Subscription Subscribe(std::string_view eventType, Handler handler);
  void Unsubscribe(Subscription sub);

  // Safe from component code during a tick. Appends to nextQueue_.
  void Publish(GameEvent event);

  // Called only by GameLogicSystem during the event phase.
  void DispatchQueued(uint64_t tickIndex);

  std::span<const GameEvent> RecentEvents() const;
};
```

Dispatch rules:

- `Publish()` appends to the next queue.
- At the event phase, current and next queues are swapped.
- Handlers run in FIFO order by event sequence.
- Events published by handlers run on the next dispatch cycle, not recursively.
- Entity/component create/destroy requests made by handlers are deferred until the mutation phase.
- A fixed-size event log ring buffer keeps recent events for DevGui.

## NavMesh & AI Integration Details

### Path Following with Detour

```
State: MoveToState
  │
  ├─ NavigationWorld::FindPath(currentPos, targetPos)
  │   → Returns Detour path (polygon refs + corner points)
  │
  ├─ PathFollower::Update(dt)
  │   ├─ Compute desired velocity toward next corner point
  │   ├─ FlockBehavior::CalculateSteering() (separation from nearby units)
  │   ├─ Clamp to max speed and max force
  │   └─ KinematicCharacterController::Move(desiredVelocity)
  │
  ├─ Path validation each frame
  │   ├─ Check if current polygon is still valid
  │   ├─ Re-path if blocked (dynamic obstacle)
  │   └─ Emit PathBlocked event if re-path fails
  │
  └─ Arrival check
      ├─ Distance to target < arrivalThreshold
      ├─ Emit Arrived event
      └─ Transition to next state (e.g., Idle or Attack)
```

### Group Movement with Detour

- Each unit in a formation gets its own path, offset from the formation center point
- `FlockBehavior::separationWeight` prevents unit overlap during movement
- Formation target positions are recalculated each frame based on group velocity and direction
- If a unit's path is blocked, it requests a re-path with a slight position offset (jitter) to find an alternate route
- DetourCrowd is detected by the navigation backend but is not the active SceneTemplate path today. Treat DetourCrowd as a later optimization, not a dependency of the first implementation.

### Line of Sight (Combat)

```cpp
// In AttackState or SensorComponent
bool CheckLineOfSight(const Vec3& from, const Vec3& to, JoltPhysicsSystem& physics) {
    // Use Jolt's ShapeCast with a thin capsule/box from 'from' to 'to'
    PhysicsSettings::ShapeCastSettings settings;
    settings.m_returnFirstHit = true;

    // Thin capsule for LOS ray
    Ref<Shape> losShape = new CapsuleShape(CapsuleShape::Settings(0.1f, 0.1f));

    Vector3 direction = (to - from).Normalized();
    Vector3 displacement = direction * distance;

    ShapeCastResult result;
    physics.GetSystem()->ShapeCast(losShape, from, from + displacement,
                                    Quaternion::sIdentity(), settings, result);

    return result.mFraction >= 0.95f;  // Reached target without obstruction
}
```

### Scene Loading Integration

```cpp
// In SceneTemplate::OnLoadScene → GameLogicSystem::OnLoadScene()
// Uses SHARED framework types from Framework/include/scene/EditorSceneFile.h
bool GameLogicSystem::LoadFromScene(const t850::scene::EditorSceneFile& sceneFile,
                  const GameSceneRuntimeLinks& links,
                  t850::scene::SceneValidationReport* report) {
  auto localReport = t850::scene::ValidateEditorSceneGameLogic(sceneFile);
  if (report) *report = localReport;
  if (localReport.HasErrors()) {
    return false;
  }

    // Configure spatial grid from global settings
    if (sceneFile.game_logic_settings.has_value()) {
        const auto& settings = sceneFile.game_logic_settings.value();
    ConfigureSettings(settings);
    }

    // Create game objects from scene game_entities (shared vector<SceneGameEntityDesc>)
    for (const auto& entityDesc : sceneFile.game_entities) {
    GameObjectLinks resolvedLinks = links.Resolve(entityDesc);
    GameObject* object = registry_.Create(entityDesc, resolvedLinks);
    if (!object) continue;

        // Deserialize components from shared SceneComponentDesc vector
        for (const auto& compDesc : entityDesc.components) {
            if (!compDesc.enabled) continue;
      auto component = componentFactories_.Create(compDesc, *object, *this);
      if (component) object->components.push_back(std::move(component));
        }

        // Deserialize state machine from shared SceneStateMachineDesc
        if (entityDesc.behavior.has_value()) {
      AttachStateMachine(*object, *entityDesc.behavior);
        }
    }

  // Groups are phase 6. When implemented, resolve members through stable entity IDs.
    for (const auto& groupDesc : sceneFile.game_groups) {
    LoadGroupByStableIds(groupDesc);
    }

  return true;
}
```

## Phased Implementation Plan

### Phase 0: Source-Grounded Decisions

Decide and document before coding:

- stable ID format and generation helper;
- scene version that introduces game-logic IDs/components;
- `behavior` is optional (`std::optional<SceneStateMachineDesc>`);
- fixed tick rate and max catch-up ticks;
- queued event dispatch rules;
- unknown component behavior: warning and preserve data;
- validation/migration function names and ownership;
- MSBuild and CMake file update policy.

Deliverable: this proposal updated and checked in.

Files:

## Testing Requirements

Minimum test/verification coverage:

- Schema round-trip for `SceneComponentDesc` and extended `SceneGameEntityDesc`.
- Migration generates missing IDs and preserves them on save/load.
- Duplicate IDs are validation errors.
- Runtime registry creates, finds, and destroys objects by runtime ID and scene ID.
- Component lifecycle callback order is deterministic.
- Event handler publishing queues the new event for the next dispatch cycle.
- State-machine priority/cooldown/wildcard behavior is deterministic.
- SceneTemplate load/unload leaves registry empty after shutdown.

## What This Does NOT Do

- Does not introduce a separate scene format; it extends `EditorSceneFile` / `.t8scene`.
- Does not make T8ditor own runtime game logic; runtime logic lives in `Framework/game` and is first hosted by SceneTemplate.
- Does not require a full ECS in the first implementation.
- Does not require visual scripting or a node graph before list/table state-machine editing works.
- Does not make RTS groups, formations, flocking, combat, or resources mandatory engine core.
- Does require build project updates when new `.cpp` files are added: at minimum `Framework.vcxproj`, and `Framework/CMakeLists.txt` while CMake remains maintained.
