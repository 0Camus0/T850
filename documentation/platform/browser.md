# Browser Runtime

Status: Firefox runtime stability and seven default scene launches validated,
2026-09-16. All seven runtime scene classes compile into the WebAssembly
executable and render their selected content. This is not a browser T8ditor port
or a claim that every authoring, persistence, and gameplay workflow is covered.

## Build and Run

After PR #40 integration, `?postProcessMode=compute` selects the shared compute
post-processing kernels; `raster` remains the default. The launchers forward their
existing Raster/Compute selector. Minecraft torch particles currently have only
a compute implementation, so Raster mode leaves that layer empty.

`BuildWeb.ps1` exports version-3 graphics/compute packages, all selected scenes
in both execution modes and all three shader flows, and the shared compute correctness kernels. Rebuild
without `-SkipShaderExport` after upgrading from the older package schema.
`?shaderFlow=wgsl` requires direct WGSL; `?shaderFlow=spirv` requires the offline
HLSL -> SPIR-V -> Tint WGSL path. `auto` prefers direct WGSL and permits fallback.
Package identity includes the requested flow, and the recorded source provenance
is checked when loading strict modes. Browsers consume prepared WGSL in both
cases; they do not run an HLSL/SPIR-V compiler.
`?computeSelfTest` runs arithmetic and odd-sized image GPU readback tests instead
of the scene. For example, with the local server running:

```powershell
node .\web\test-firefox.mjs --browser chrome --compute-selftest --url 'http://127.0.0.1:8765/?computeSelfTest'
node .\web\test-firefox.mjs --browser chrome --compute-selftest --url 'http://127.0.0.1:8765/?computeSelfTest&shaderFlow=wgsl'
node .\web\test-firefox.mjs --browser chrome --compute-selftest --url 'http://127.0.0.1:8765/?computeSelfTest&shaderFlow=spirv'
```

Both Chrome and Firefox passed this test after integration. Real feature-removal
Chrome tests also passed compute Minecraft with touch, OnTop and camera controls;
physical phone validation remains separate. Use `--no-interactions` for the
touch harness: its desktop mouse test expects pointer lock, which Touch prevents.

From the source directory containing `T850.sln`, on the Windows development host:

```powershell
$env:T850_BUILD_WORKERS = '4'
.\scripts\BuildWeb.ps1
node .\web\server.mjs
```

Open `http://127.0.0.1:8765/` in Firefox. Minecraft is the authored default in
`web/scenes.json`; the selector exposes all runtime scene IDs. Click the canvas
to request pointer lock. Existing Minecraft controls and GUI remain unchanged.
The server is loopback-only and never exposes arbitrary workspace files.

Both Launcher and Launcher Release offer separate entries:

- **WebGPU (Dawn/D3D12)** launches the selected native x64 or ARM64 executable.
- **WebGPU + Browser (Emscripten)** reveals a **Browser** dropdown, starts the
  Node server and opens the selected browser. RUN becomes OPEN BROWSER. Scene,
  model/document, maximum canvas dimensions, culling, post-process mode, and log level are passed
  through URL parameters; scene-specific overrides clear when the web selector
  changes scenes. Native shader flows, fullscreen, dumps, replay, telemetry,
  benchmark, and editor controls are disabled in this mode.

Both launchers discover registered Windows browsers, with install-path fallbacks
for Chrome, Firefox and Edge. Internet Explorer is excluded. **System default**
remains available; installation alone does not prove WebGPU support on an adapter.
The list refreshes when opened, shows executable paths in tooltips, and remembers
the selection in `webBrowser` in `config.json`. A saved browser that has been
removed falls back to System default on reload. Browser selection is hidden for
native APIs and is never passed to native executables.

The development launcher provides **BUILD WEB** and **REBUILD WEB** using
`scripts/BuildWeb.ps1`, including native shader export. The configuration selector
chooses Release or Debug; native architecture does not affect the browser build.
The Emscripten output is WebAssembly and JavaScript, not an x64 or ARM64 PE binary;
one completed bundle runs unchanged in supported browsers on either host architecture.
REBUILD WEB passes `-Clean`, removing only generated `build/web` output, then
regenerating shaders and compiling dependencies and the runtime. The SDK, native
builds, assets and saved config are retained. BUILD WEB can also initialize an
absent output directory. Both configurations share `build/web`, so OPEN BROWSER
runs the most recently completed build. The output panel shows build progress
and errors. A release launcher
inside this checkout can find the source browser build; a portable release needs
`web/server.mjs`, `web/site/` (HTML/JS/Wasm/catalog), `web/WebShaders/`, and
`web/assets/` (the asset directory contents) beside the executable. These files
are not generated by compiling the launcher alone. Node.js must be on PATH.
Missing prerequisites disable OPEN BROWSER and report what is missing.

### Stale Browser Builds

OPEN BROWSER launches the last completed Emscripten build; building native
Debug/Release or updating the launcher executable does not update it. After
pulling scene-code, schema, or compute-shader changes, use BUILD WEB before
launching. The Wasm executable and prepared shader packages must come from the
same source version. Do not use `-SkipShaderExport` for that refresh.

An older browser executable may ignore newer scene fields, so structures added
in native code can be absent. A newer shader source without matching exports
fails with `Missing or invalid browser shader package` and a `WebShaders/*.json`
path; JavaScript/WebGPU errors can follow the failed compute pipeline.

An interrupted link can also leave a partial Wasm module paired with the previous
JavaScript wrapper, producing errors such as `Import #0 "env": module is not an
object or function` before any scene starts. Finish the build before reloading.
The local server rejects empty runtime files at startup. Its reuse identity
includes runtime file size/timestamps, and it returns HTTP 503 with restart
instructions if runtime files change after startup instead of serving a mixed
build. Reopening from the launcher selects a server for the new runtime.

For a focused Minecraft and Day Scene refresh from the source directory:

```powershell
.\scripts\BuildWeb.ps1 -Configuration Release -ExportScenes 6,1
```

Restart the local server after exporting shaders, then reload the browser tab.
The server catalogs shader filenames at startup. A server started before the
export can retain an obsolete catalog even though the new files exist on disk.
The normal BUILD WEB command exports all scene defaults; the command above
limits only the scene startup exports to Minecraft and Day Scene.

### Pointer-Lock Denial

Embedded or restricted documents can reject mouse capture with `WrongDocumentError`
or another recognized pointer-lock permission/state error. The canvas handles
these rejections at `requestPointerLock`, records a nonfatal `pointerLock`
diagnostic, and keeps rendering. A later user gesture may retry capture.
Unexpected exceptions still reach the ordinary fatal error handler; rendering
errors are not filtered by matching their message. Standalone Chrome's
`--pointer-lock-recovery` harness verifies a denied request, advancing frames,
and a subsequent successful capture. In v0.1.9, previous-run reports are available
only inside the opt-in engine console, not the current-run error overlay.

### Wasm Streaming Retry Diagnostics

Fixed in v0.1.9: the iPhone screenshot supplied on
2026-09-18 shows **Previous run: runtime error**, the current status **Running**,
and a rendered Minecraft scene. Its saved message is
`wasm streaming compile failed: TypeError: Load failed`. That screenshot alone
does not establish a first-frame GPU failure or explain the original fetch
failure (it was taken on a cellular connection).

The pinned Emscripten loader emits that stderr message and
`falling back to ArrayBuffer instantiation`, then retries with a full download.
The old shell classified every stderr message as fatal and retained the first
one even when the loader recovered. The correction recognizes only those
two messages from `Module.printErr` before runtime initialization, retains them
in the log and marks `wasmStreamingFallback`, without declaring a fatal error.
An ArrayBuffer failure, abort, uncaught exception, engine error or later stderr
message still follows the normal fatal path. No shader validation is disabled.

Saved reports no longer show the error overlay at all. With **Show engine logs**
enabled, a collapsed **Saved report from previous run** section in the console
provides the old details; copy/download includes that clearly labeled history.
Current-run errors still open automatically. Earlier diagnostics are retained,
not silently deleted. A real freeze needs the current run's logs and frame state
rather than the retained report alone.

Eighteen Node tests pass, including true fallback failures and errors after
initialization. A Chrome regression seeds the screenshot's prior report and
rejects exactly the first Wasm fetch. It reproduces the false fatal state before
the fix; after rebuilding, it makes two fetch attempts, reaches Running with
zero errors, advances another 90 frames at the explicit progress check, and
preserves the old report without showing a popup. This reproduces the loader
condition, not the original iPhone network cause.

### Launcher Console Logs

The v0.1.8 WSSI launcher includes an unchecked **Show engine logs** checkbox.
Checking it launches with `logLevel=trace`, enabling error, info, debug, verbose
and trace messages through the existing engine logger, browser console and a
visible **Engine console** panel on the game page. The panel opens before the
Wasm runtime starts, so startup failures are visible without developer tools.
Unchecked keeps `logLevel=error`. The URL carries the selection, and returning
to the welcome page preserves it; a fresh launcher URL defaults to unchecked.
The explicit launch option overrides the catalog's `info` default because the
engine uses the last `--logLevel` argument.

The panel can collapse to its summary bar. **Follow** is enabled by default;
turning it off preserves the reading position while messages continue arriving.
Copy, download and clear controls use local Lucide icons. Text exports contain
the current state, scene, browser, framebuffer dimensions, reported Wasm memory
and recent messages. Clipboard permission failures are nonfatal, with download
as an alternative. No external log service or developer mode is required.

The panel and exports retain the latest 4,000 messages, keeping memory bounded;
browser-console forwarding is not truncated. Normal DOM updates are batched at
250 ms, and errors flush immediately. Clearing logs does not erase the separate
first-error report. It shows existing logged operations, not every function
call. Trace logging can affect performance. The full log buffer is not persisted
across navigation, and an OS-terminated browser process may never deliver its
last message; the panel is not a guarantee of crash recovery. The local reload
diagnostic checkpoint described below retains only a small recent snapshot.

On 2026-09-18, 17 Node tests and Chrome/Firefox console workflows passed.
Checks cover default-hidden behavior, startup output, immediate failures,
bounded history, denied clipboard access, collapse/reopen, manual Follow,
desktop/portrait/landscape layouts and return-state preservation. Chrome also
created a real text download; clipboard writes were stubbed in browser tests
to avoid modifying the user's system clipboard. The narrow Chrome viewport was

### Silent iPhone Reload Investigation

Diagnostics published in v0.1.10: the owner reports the iPhone
tab reloading about five seconds into play. The runtime has no inactivity reload
timer. Safari web-content termination, GPU-process failure or memory pressure
remain hypotheses; no physical-device crash report establishes the cause.

A bounded headless Chrome check used phone-sized metrics and touch input, but
still ran on the desktop NVIDIA GPU, not WebKit or iPhone hardware. Both logging
off and trace-on runs survived 30 seconds. At the last samples, Wasm heap capacity
was 256 MiB in both cases. The page's reported JavaScript heap was about 6.6 MiB
without logging and 12.2 MiB with trace, which emitted 66,410 messages in 26.1
seconds. This measures neither the GPU process nor total browser memory and is
not evidence that Safari cannot run out of memory. Detailed trace logging adds
substantial work; test the phone with **Show engine logs** unchecked first.

The shell now writes a small checkpoint to `sessionStorage` every two
seconds, including state, last startup stage, frame count, Wasm heap capacity,
render dimensions, visibility, logging mode, browser user agent, and at most eight 512-character
log excerpts. Normal `pagehide` and caught errors are marked separately.
Timers stop on `pagehide` and restart without duplication on `pageshow`.
The next load retains the snapshot under **Previous run diagnostics** inside
the opt-in console and in copy/download output. It never opens an old-error
popup. A checkpoint marked `active` means no later lifecycle update was retained,
not proof of a crash; a browser may also discard session storage entirely.

Before another startup replaces that checkpoint, the last played or failed
session is retained separately under `t850:previous-session:v1`. Repeated reloads
that stop during Loading do not erase that useful snapshot. The launcher reads
these small records and the last captured engine error without starting Wasm.
When records exist, its collapsed **Saved diagnostics** section provides their
JSON and a download action. It stays available even if WebGPU initialization is
unavailable, does not relaunch the game, and never clears the saved evidence.
Normal launcher visits with no saved data show no extra panel. Browser-owned
error pages or process kills may not dispatch JavaScript errors, so an absent
engine error still does not rule out either GPU failure or memory pressure.

Tests cover bounded data, restoration, malformed storage, lifecycle cleanup and
current-error reporting. A real local browser reload preserved a snapshot with
1,860 frames and 256 MiB Wasm capacity, correctly labeled `pagehide`, and kept the
error overlay hidden. No rendering limits, GPU lifetimes or frame scheduling
were changed. This adds evidence for a phone retest, not a claimed reload fix.
A follow-up headless Chrome check retained the played session through reload
and downloaded it from the launcher with zero Wasm/runtime requests there.
Phone (390 CSS pixels) and desktop layouts passed, as did 19 web tests including
repeated startup interruption, malformed/denied storage and download generation.
Neither test reproduces the physical iPhone restart. These diagnostics shipped
with v0.1.10; they do not establish or fix the original restart cause.
Evidence: `%LOCALAPPDATA%/T850Profiles/iphone-reload-20260918`, with the follow-up
under `launcher-recovery`.

### Server Reuse

Server launch reuses a matching server at port 8765, including its catalog
identity. An occupied port belonging to another app/build is left untouched;
launch tries the next port, up to thirty additional ports. The server console
shows the selected URL and errors and stays open while serving the browser.
An explicit selection is passed as `--browser "C:\path\to\browser.exe"` to the
server, including when reusing a matching server. Missing executables are rejected
instead of silently opening another browser.
The engine emits an explicit `t850-runtime-ready` event after initialization,
so the portable launcher's error-only logging still transitions the page to
Running. Chrome and Firefox readiness/capture/resize checks passed at that log
level; startup no longer depends on the informational ready log.

`BuildWeb.ps1` installs Emscripten 6.0.9 in the user-local T850 SDK directory,
checks the matching Emdawn port's SHA-256, builds the native shader exporter,
exports the recorded permutations plus all seven scene startup shaders, then builds
the browser executable and runs the existing Framework tests as Wasm in Node.
Use `-SkipShaderExport` only when the prepared shader package is current.
`-ExportScenes` can restrict startup exports; its default is `6,0,1,2,3,4,5`.
Exports use the same per-scene model/document arguments as `web/scenes.json`
and reject engine error logs, not just nonzero exit codes. Exports require native
assets and do not themselves validate browser rendering. `-CMake` and
`-EmSdkRoot` select installed tool locations.

Asset delivery is explicit:

- `-AssetMode Embedded` is the default. It retains the full local scene-startup
  shader export used by the existing embedded Minecraft package. The deployment
  preparation step creates the content-addressed asset ZIP; asset binaries remain
  ignored and are never committed.
- `-AssetMode Cloud` compiles the checked-in graphics/compute permutation manifest
  without launching asset-dependent native scenes. It writes only
  `build/web/CloudAssets/routes.json`, a validated catalog of public model/texture
  URLs. `server.mjs` proxies a resource only when the browser requests it, while
  tracked scenes, shaders, fonts and small source assets remain local. No cloud
  model or texture bytes are downloaded into the build or included in the package.

CI uses `-AssetMode Cloud -Clean`, uploads `site/`, `WebShaders/` and the small
route catalog, and runs the same package in native x64 and ARM64 Edge jobs. This
keeps CI independent of the ignored local asset library and prevents the web
artifact from carrying the 1.61 GiB runtime payload.

Fresh builds require Git, CMake, Ninja, Node.js, the Windows x64 MSVC toolchain
and the native project dependencies. Embedded mode also requires its local scene
asset payloads; Cloud mode requires the tracked sources and access to the pinned
public manifests, but does not download their payloads. The script installs/activates
the pinned Emscripten SDK and runs native Dawn setup. SDK and shader-export stdout
and stderr are captured together and checked by process exit code, avoiding
PowerShell 5.1 treating informational native stderr as a failed build. Quoted
executable and log paths support spaces.

If BUILD WEB reports that `Get-FileHash` is not recognized immediately after SDK
activation, check how the launcher was started. A PowerShell 7 host can pass its
`PSModulePath` through the launcher's `cmd.exe` logging wrapper into Windows
PowerShell 5.1. That child can discover incompatible PowerShell 7 modules before
its own built-in modules. This is an environment failure before compilation,
not a missing shader or a bad SDK checksum.

The development launcher's logged-process runner now removes `PSModulePath`
only from Windows PowerShell child processes, letting 5.1 initialize its own
search path. It does not change the parent/system environment or other child
processes, and the pinned SDK SHA-256 check remains mandatory. Reopen
`scripts/Launcher.ps1` after updating it. `scripts/TestLauncherWebGPU.ps1`
includes a real child-process hashing check with an intentionally incompatible
module search path, plus parent-environment and non-PowerShell isolation checks.

### Browser CI Architecture

GitHub Actions builds the Release WebAssembly bundle once in the native x64
Release cell and uploads `site/`, `WebShaders/` and `CloudAssets/routes.json` as
`T850-Web-Release`. Separate
x64 and ARM64 jobs download that exact artifact, verify the PE machine type of
their installed Edge executable (`0x8664` or `0xAA64`), serve the bundle locally,
and run the same compute correctness test. There is no separately compiled ARM64
Wasm artifact.

Standard hosted Windows runners do not provide a hardware GPU. CI therefore uses
the explicit `--software-webgpu` harness mode, which selects Chromium's SwiftShader
WebGPU adapter and fails unless adapter metadata identifies it as fallback/software.
The JSON report records `webgpuMode`, browser version, adapter identity and limits.
This gate validates browser/Wasm startup and arithmetic plus odd-sized image compute
correctness on native x64 and ARM64 browser processes. It does not establish hardware
adapter support, frame-time performance, presentation behavior or native Dawn GPU
execution; those remain hardware-runner or local-machine tests.

Release REBUILD WEB regenerated all shaders, compiled 637 build steps and passed
Wasm self-tests. Debug BUILD WEB and a subsequent Release BUILD WEB also passed
through the actual launcher build handler under Windows PowerShell 5.1. Installed
toolchains, native dependencies and assets were reused; this was not a clean-OS
installation test. Both launcher executables were rebuilt. Command/WPF tests
cover browser discovery, selection, config round trips, native-mode isolation,
and Build/Rebuild routing. The portable launcher remains run-only.

### Input and Resize Regression

A reported loss of Minecraft input reproduced as a renderer freeze during
resize on 2026-09-16. SDL had already published a new window size while the
current render target still used the previous size. ImGui generated a 500x671
scissor for an 884x551 target; WebGPU validation rejected it and the runtime
stopped its frame loop. The browser ImGui backend now uses the driver's current
render dimensions for its display size and framebuffer scale. Native GUI sizing
is unchanged.

The same sustained-walking/GUI/resize sequence passed after the fix. Firefox
156.0, Chrome 152.0.7977.83, and Edge 153.0.4234.32 then passed at an actual
1920x1080 render size with full culling, three 1,200-frame held-key intervals,
mouse-look, GUI toggles and desktop/narrow resize. Chrome and Edge additionally
cycled canvas focus and pointer lock. SDL key/mouse counters advanced and the
player-position logs changed in all three runs. The user confirmed normal input
after a hard reload. Edge's initial black-screen report did not reproduce and
the user subsequently confirmed it started; no Edge-specific rendering change
was made. The older intermittent Wasm out-of-bounds failure is not proven to
share this resize cause.

Evidence is under `%LOCALAPPDATA%/T850Profiles/browser-input-20260916/`:
`firefox-held-input/` retains the failed scissor validation and
`{firefox,chrome,edge}-held-resize-fixed/` retain the passing runs. Reproduce with:

```powershell
node .\web\test-firefox.mjs --browser firefox --url 'http://127.0.0.1:8765/?scene=6&width=1920&height=1080&culling=full&logLevel=info' --maximize --input-rounds 3 --hold-frames 1200 --gui --output "$env:LOCALAPPDATA\T850Profiles\browser-input"
```

`--focus-cycles` adds pointer-lock release and reacquisition between input rounds.
`--maximize` is important when testing the requested resolution: the default
test window can otherwise constrain the canvas below the URL dimensions.
The harness retains DOM focus/key events and engine input snapshots, verifies
the forward key stays held until keyup, and checks continued SDL key/mouse event
delivery. These distinguish live rendering with blocked input from a stopped
worker; frame counts or changing animation alone do not prove walking works.

### Reusable Cloudflare Deployment

`web/deploy-pages.mjs` consumes a local JSON config, prepares the existing
browser build, and deploys it with the pinned Wrangler dependency. It does not
build C++, create Pages projects or R2 buckets, upload/delete R2 objects, change
bucket access, or delete old deployments. Those are separate explicit operations.
Create a Direct Upload Pages project first. Only the multi-scene package needs
populated R2 buckets; the current Minecraft deployment is a static bundle.

```powershell
npm ci --prefix .\web
if (!(Test-Path .\web\cloudflare.local.json)) {
  Copy-Item .\web\cloudflare.example.json .\web\cloudflare.local.json
}
# Edit the local JSON, and supply CLOUDFLARE_API_TOKEN securely in this process.
npm run pages:deploy --prefix .\web -- --dry-run
npm run pages:deploy --prefix .\web
```

Do not overwrite an existing local configuration with the example. All
`cloudflare*.local.json` files are git-ignored; only the placeholder example
belongs in version control. `--config PATH` selects a different local config
for packaging, deployment or local preview. Relative explicit paths resolve
from the command's working directory (npm with `--prefix web` runs in `web`).

Configuration fields:

- `projectName`: your existing Pages project name.
- `accountId`: your 32-character Cloudflare account ID.
- `apiToken`: optional local token; prefer `CLOUDFLARE_API_TOKEN`, which takes
  precedence. A scoped token with Pages edit access (plus R2 binding access for
  the multi-scene package)
  is required for deployment. Missing tokens fail before any child process or
  network request, even if Wrangler has a cached OAuth login. Invalid or
  insufficient tokens are rejected by Cloudflare. Dry runs validate settings
  and presence of credentials without making network requests or validating
  them with Cloudflare.
- `branch`: deployment branch, default `main`; use the project's production
  branch to replace its production deployment, or another branch for a preview.
- `minecraftOnly`: default `true`; `false` prepares the separate all-scenes
  package. Asset availability and pending uploads must be checked for that mode.
- `r2Buckets`: optional/unused for `minecraftOnly: true`. Multi-scene mode requires
  the `MODELS` and `TEXTURES` bindings, each with your `bucketName`
  and a public HTTPS `manifestUrl`. Each manifest has an `assets` array with
  `url`, `key`, `kind`, and optional `localRelativePath`, `size`, `contentType`.
  Asset URLs must belong to the configured public origins; credentials/query
  tokens in those URLs are rejected. Local assets must match your manifests.

The token is passed only in the deploy subprocess environment, never in command
arguments, browser assets, dry-run output or generated Wrangler JSON. Invalid
JSON errors withhold file contents. Keep configuration outside asset/output
directories; the script rejects those paths. Git ignore is not encryption and
can be bypassed by `git add -f`: protect the local file, prefer environment
credentials, and rotate any token previously shared or committed.

Pages requires the standard `wrangler.jsonc` filename. The script generates it
in an ignored temporary `build/cloudflare/deploy-*` directory, containing only
project/output/bucket settings, and removes it on normal completion or
a handled failure. Interrupted runs may leave only ignored temporary state.
The account is passed through `CLOUDFLARE_ACCOUNT_ID`, not `account_id` in the
generated file. Wrangler 4.133.0 accepted that field during local preview but
rejected it during the first actual Pages deployment; the corrected schema is
regression-tested and was used successfully for v0.1.4. The API token remains
only in the deploy subprocess environment.
Multi-scene production uses R2 bindings and never sets `ASSET_SOURCE=public-mirror`.
If multi-scene packaging finds oversized resources not in the configured manifests, it
writes an upload list under `build/pages-r2/` and refuses to publish. Populate
the named buckets with the listed keys and add them to their manifests before
rerunning deployment. This avoids publishing a site with missing assets.

For a token-free local preview, use `npm run pages:dev --prefix .\web` (port
8788, configurable with `-- --port 8791`). It prepares the selected package and

does not authenticate to Cloudflare or write to real R2. It cannot serve pending

### Embedded Browser Isolation

On 2026-09-17, the owner reported `Cross-origin isolation is unavailable` in
an Instagram in-app browser. A live HEAD check of `/`, `/minecraft-wssi.html`
and `/DayScene?demo=wssi&scene=6` returned HTTP 200 with both
`Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp`. No restrictive Permissions-Policy
header was returned. Those requests confirm the server configuration, not the
behavior of the owner's embedded browser or any intermediary it uses.

The runtime uses shared Wasm memory and pthreads. An embedded WebView or its
hosting policy can leave `crossOriginIsolated` false even when direct requests
receive the correct headers. WebGPU availability is a separate requirement.
See [MDN's isolation requirements](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated).
Do not disable the guard or weaken security headers: that cannot provide the
shared memory required by this build.

Use the host app's menu to open the link in an up-to-date standalone Safari,
Chrome, Edge or Firefox. A web page cannot reliably force an embedded browser
to launch an external one; `target="_blank"` may simply open another in-app
view. Supporting a non-isolated browser would require a separately engineered
non-threaded runtime and still require WebGPU and sufficient GPU limits, not
just a launcher switch.

The guidance change prepared as v0.1.3 is published in v0.1.4. It replaces the
generic isolation error with that standalone-browser guidance. Launch remains
disabled and adapter initialization is not attempted. The unit test covers this
blocked state. This is a messaging improvement, not verified Instagram WebView
support; no physical-device test is implied.

### Touch and Optional GPU Features (v0.1.2)

The original v0.1.2 behavior enabled controls from `maxTouchPoints`, a coarse
pointer, or the first touch event alone. Release v0.1.8 separates
input capability from the automatic default:

- Android phones/tablets and iPhone/iPad default to the touch gamepad when touch
  input is available. Android tablets do not require the phone-only `mobile`
  client hint to be true.
- Windows and ChromeOS stay off by default even with touch. Other desktop or
  unknown platforms also stay off unless mobile platform signals are present.
- Desktop-mode iPad uses the established Macintosh/MacIntel plus more than one
  touch point heuristic. Browser APIs cannot guarantee a physical device class;
  spoofed/desktop-mode user agents and future touch Macs can be ambiguous.
- A touch-capable desktop still offers the Touch checkbox, but a finger tap

`web/touch-controls.js` publishes axes and button state through an eight-slot
atomic buffer. `WebFramework::ReadTouchInput` reads it on the engine worker and
maps it to the existing gamepad API. Pending press bits preserve short taps
between polls. This does not synthesize keyboard events or proxy per-frame
input synchronously to the page thread.

The block atlas (`Textures/terrain.png`) is not BC-compressed. The default
`sky/CubeMap_SkyWater.dds` is BC1/DXT1, 1024-square, six faces and eleven mip
levels. Without BC support the shared bounded DXT1/3/5 decoder uploads all faces
as RGBA8. Starting in v0.1.6, WebGPU chooses the first available source mip at
or below 512x512 and retains the smaller levels. The default sky thus uploads
512x512 through 1x1 (ten mips), using about 8 MiB rather than the former 32 MiB.
Downloads stay compressed and the supported-device BC path remains full-size.
The shared decoder's default `firstMip=0` preserves Vulkan's existing behavior;
only the WebGPU no-BC cubemap caller requests mip skipping. Small cubemaps and
2D textures are unchanged. An incomplete mip chain can only select its smallest
available mip; this is not a general-purpose resize operation. Non-BC raw/HDR
skies and generated float IBL resources are outside this particular memory limit.
Wasm tests cover cube/mip order, asymmetric face orientation, truncated data,
transparency, and BC2/BC3 color interpolation.

Without `float32-filterable`, nearest-sampled float data stays RGBA32F with
unfilterable-float texture bindings and non-filtering samplers. Updates preserve
full-precision bone matrices and tiled-light data. Filtered float cubemaps use
RGBA16F with finite values clamped to its range; the capable-device path stays
RGBA32F. Depth stays 32-bit and uses nearest sampling rather than a filtered
R32Float copy on unsupported devices, preserving depth precision at the cost
of potentially less smooth shadow edges. Half-float conversion is self-tested.

The compatibility test uses `--disable-bc --disable-float-filtering` (Chrome or
Edge) and attaches to workers before startup. A page-only override does not
affect the GPU-owning worker. It requires the device log to report
`BC=0 float32-filterable=0` and a six-face BC decode log, in addition to frame
progress, nonblank captures and touch interaction checks. It also asserts the
default 512-to-1 mip chain and 8,388,600-byte decoded payload. Earlier `--no-bc`
runs did not actually disable the feature and are not compatibility evidence.

- `WebFramework` owns the SDL canvas, browser input, platform clock integration
  and lifecycle. No browser backend code is added to Minecraft or other scenes.
- Emdawn maps the shared WebGPU driver to browser WebGPU. Native HWND/DXGI
  handling remains native-only. Firefox selects its underlying GPU backend.
- The browser build uses pthreads, SIMD and Asyncify with Emscripten C++
  exceptions. The application runs on a worker with an OffscreenCanvas; the UI
  thread remains available for input and filesystem proxy work.
- Frame callbacks use a worker-local `MessageChannel` dispatcher installed into
  the pinned Emscripten `MainLoop.setImmediate` hook. Emscripten still owns
  iteration, cancellation, and Asyncify pause/resume. This avoids the nested
  timeout delay and the SDK's main-thread message fallback; ordinary GPU work
  remains bounded by completion tracking. Revalidate the hook on SDK upgrades.
  Every eighth callback yields through `setTimeout(callback, 0)` for scheduling
  fairness instead of dispatching an uninterrupted stream of channel messages.
  Paused applications use a 100 ms timer for input polling instead of a busy
  immediate loop; active rendering restores worker-local dispatch.
  Callback throughput is not the browser compositor's displayed refresh rate.
- Replaced GPU buffers and textures retire through the WebGPU context. Buffers
  follow submission completion futures and are reused only after all
  referencing commands complete, keyed by allocation size and usage, with a
  32 MiB cap on the free pool. Texture retirement still uses explicit Destroy
  after submission; WebGPU retains submitted uses until execution completes.
  Readback staging and replaced resize textures are explicitly destroyed too.
  On a size/usage cache miss, completed unused allocations can be evicted to
  leave room for reuse of the newly requested class, rather than permanently
  filling the pool with startup-only resources.
- Uniform data uses immutable, 256-byte-aligned snapshots in 1 MiB pages. Pages
  are uploaded once per submission and recycled through the same completion
  mechanism. A submission epoch invalidates old snapshots even when a constant
  buffer's CPU contents have not changed; mid-frame readback cannot cause a
  following draw to reuse a stale page offset.
- Dynamic uniform offsets allow reuse of a shader layout's last bind group.
  Buffer/view/sampler identities and static offsets are compared before reuse.
  Binding descriptors are retained and updated in place; unchanged draws do
  not allocate a descriptor vector or copy all its reference-counted handles.
  Pipeline keys are typed values, and attachment formats are cached at target
  binding rather than queried from GPU objects on every draw. Validation is
  retained; success paths no longer build detailed diagnostic strings.
- Both WebGPU targets keep a bounded set of submitted batches. BeginFrame polls
  completion and waits only for the oldest submission when four are outstanding,
  rather than draining the entire queue every fourth frame. Browser waits yield
  through Asyncify. Native WebGPU selects Immediate presentation when supported,
  matching native D3D12's uncapped policy; browser presentation remains FIFO.
- Browser runtime GUI panels are constrained to the current drawable viewport,
  retaining access to controls and close buttons after a window shrink.
- ResourceLocator downloads only cataloged requested assets and caches them in
  the session's `/assets` virtual filesystem, not the generated-data cache.
  This avoids retaining outdated authored assets across reloads or deployments;
  a persistent download cache would require content versioning or HTTP
  revalidation before reuse. The local preview server streams current files on
  each request with `Cache-Control: no-cache`; its reuse identity tracks paths
  and catalog membership, not cached file contents.
  The catalog includes all available authored scenes,
  assets and prepared shaders, excluding hidden native cache directories.
  Generated runtime data is rooted at `/persistent`, mounted as IDBFS with
  automatic persistence. Reload/save durability still needs explicit testing.
- Shader packages contain prepared WGSL and reflection metadata. Request hashes
  include source, defines, key, stage and entry point; payload hashes protect
  the package contents. Missing/stale/corrupt packages fail explicitly. Re-export
  after shader changes. Runtime HLSL/SPIR-V compilation is not shipped in Wasm.
- Native compilation remains responsible for shader translation/reflection.
  The maintained WGSL quad shader now concretizes a constant `mix` operand to
  `f32`, accepted by both Tint and Firefox's WGSL implementation.
- Surfaces without `CopySrc` use a readback-capable engine output texture and a
  final presentation copy. Canvas acquisition happens at submission, after
  yielding readbacks, so browser surface lifetime does not span asynchronous work.

roughly 1,044 GPU buffers per frame. The browser profile spent 55.6 ms in the
frame, of which 30.6 ms was the amortized every-fourth-frame queue drain.

The buffer path uses the correct WebGPU lifetime model: immutable aligned
snapshots, dynamic binding offsets, batched `queue.WriteBuffer`, and
completion-gated reuse. It does not map a Uniform buffer persistently while the
GPU consumes it, as native D3D12 can with an upload heap. Most of the remaining
buffer cost is CPU preparation/copying, not one GPU write per draw. Minecraft's
per-chunk frame/instance/material constants repeat across four shadow cascades;
DayScene's regular mesh/subset path reuses substantially more data per draw.
The 2.45 MiB `webgpu.buffer_upload_bytes` Minecraft counter counts CPU shadow
updates, not actual queue traffic; use `webgpu.uniform_bytes` for snapshot data.
The [WebGPU buffer-usage rules](https://developer.mozilla.org/en-US/docs/Web/API/GPUBuffer/usage)
allow `MAP_WRITE` only with `COPY_SRC`, not `UNIFORM`;
[`queue.writeBuffer`](https://developer.mozilla.org/en-US/docs/Web/API/GPUQueue/writeBuffer)
lets the browser select the transfer mechanism for an unmapped `COPY_DST` buffer.
The pool audit did find a reuse-policy defect: DayScene's unused allocations
filled nearly 32 MiB, leaving one allocation per frame unable to enter the pool.
Evicting only completed unused buffers on a cache miss removed steady-state
allocations in a 1,200-frame profile (frames 300 onward), with one page reuse
and one uniform queue upload per frame and approximately 2.2 MiB free-pool data.
Evidence: `pool-admission-day/telemetry.json` in the follow-up profile root.

WebGPU includes descriptor/command-validation and API submission overhead;
native WebGPU versus browser also adds Wasm/JS binding calls, browser WebGPU

every compiler, IPC, or GPU cost. Identical scene data does not prove identical
GPU time: native and browser shader compilers, GPU backends, and presentation
paths can differ. WebGPU GPU timestamps remain an outstanding measurement.

### Capturing Profiles

Normal browser launch has no profiler or telemetry enabled. To capture bounded
CPU attribution with the existing layer:

```powershell
node .\web\test-firefox.mjs --url 'http://127.0.0.1:8765/?scene=6&width=960&height=540&gui' --profile-frames 1000 --output "$env:LOCALAPPDATA\T850Profiles\browser"
```

Alternatively append `&profile&profileFrames=1000` to the runtime URL. The app
pauses after the requested number of completed frames, and the JSON report is
available as `window.t850.telemetry` and in the persistent virtual filesystem.
The test saves it as `telemetry.json`. Profiling is opt-in and captures every
frame, avoiding sampling aliases with periodic queue waits.
For simulation-frame comparisons, add `&fixedDt=0.0166666667` to the profiling
URL and pass the same `--regressionFixedDt` natively. Do not use fixed timestep
for uninstrumented FPS benchmarks. `window.t850.workerTiming` publishes mean
callback interval and work time every ten frames without enabling per-draw
profiling; adjacent-window timing means can differ slightly around a slow frame.

Native equivalent, from the Release runtime directory:

```powershell
.\DayScene.exe --api webgpu --scene 6 --width 960 --height 540 --culling frustum --gui --logLevel info --profile --profileFrames 4000 --telemetry --telemetryFrequencyFrames 1 --telemetryOutput logs/webgpu-profile.json
```

Use `--api d3d12` for the reference. Completion now occurs after submission and
telemetry EndFrame; native output is flushed before exit. Literal telemetry
names no longer allocate strings when profiling is disabled, and cumulative
profiler draw/triangle counters are 64-bit to avoid long-run overflow.

### Coverage

Firefox 156.0 on this Windows host exposes WebGPU without preference overrides:
eight color attachments and 128 attachment bytes/sample. Minecraft's current
seven-target GBuffer fits this adapter. That does not establish portability to
adapters exposing only the default 32-byte attachment budget; a portable graph
or explicit unsupported-profile result is still required for those devices.

The existing 59 gameplay/terrain checks pass as Wasm, including physics, voxel
collision, navigation, shader-package integrity and the web shader-flow contract.
The original slowdown reproduced GPU out-of-memory errors after roughly 350
frames. Submission-scoped explicit resource destruction removed that failure.
Longer runs then exposed a second issue: after five minutes, browser screenshot
readback could stop worker callbacks despite an enabled loop and idle Asyncify.
Moving capture before/after pointer lock moved the failure; gameplay before
capture continued. Bounding queued frames made the same soak, movement, capture,
and resize sequence pass. This is evidence for GPU queue backpressure, not proof
of a Firefox-internal root cause.

The optimized Minecraft soak advanced over 18,000 frames with a fixed 256 MiB
Wasm heap and no engine errors. Wasm heap size is not a GPU/process-memory
measurement; the 32 MiB buffer-pool limit bounds only free pooled buffers, not
all engine/GPU allocations. All seven default launches passed rendering,
GUI-toggle, and resize checks after the allocator changes, with movement and
pointer lock checked for Minecraft and Voxel Streaming. Post-optimization
scene evidence is under the external profile root's `scenes/` directory.

each Win32/x64 Debug/Release cell. Native Minecraft final images were
