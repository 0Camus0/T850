T850 engineering report

What the WebGPU port taught us

A concise comparison of native D3D12 and Dawn/WebGPU, where the measured CPU cost occurs, and which improvements would make Dawn a better fit for high-throughput engines.

1. What did we learn?

WebGPU is a viable engine backend, but it is not a thin D3D12 wrapper. Porting successfully required treating it as a stricter execution and validation model, then separating correctness, CPU cost, GPU cost, startup cost, and presentation behavior in the evidence.

Correctness first

Black frames were usually contract defects: binding layouts, resource formats, pass compatibility, matrix translation, derivative uniformity, or lifetime errors. WebGPU exposed assumptions that native APIs sometimes tolerated.

Measure distinct boundaries

GPU timestamps, queue-drained throughput, non-wait CPU time, shader preparation, startup, and PresentMon answer different questions. FPS alone repeatedly produced the wrong diagnosis.

Presentation can dominate

An immediate-mode Dawn swapchain omitted the DXGI tearing present flag. Fixing that removed a refresh-rate throttle; it was not a shader or command-encoding problem.

Stable identities matter

Shader family, permutation, compiler flow, attachment formats, and render state must all participate in cache identity. Pointer-based or partial keys create collisions and expensive recreation.

Both shader routes need tests

Direct WGSL and HLSL-to-SPIR-V-to-WGSL can both work, but auto fallback can hide missing WGSL coverage. Strict-flow tests and reflection parity made the source paths auditable.

Recovery is an application lifecycle

Device loss cannot be solved by retrying one submission. The engine must abandon the failed device, recreate driver-owned state, reload assets, and bound the number of recovery attempts.

2. D3D12 versus WebGPU execution

D3D12 exposes the scheduling machinery. WebGPU exposes a single portable device queue and validated command-buffer model; Dawn translates that model into D3D12 queues, lists, barriers, descriptors, and synchronization internally.

3. Where is the CPU overhead?

It is not uniform across the engine. The accepted non-wait CPU study found that native Dawn's largest controllable delta is submission. Render-graph encoding contributes on x64, but it does not explain the ARM64 result. Browser WebGPU adds a much larger browser/Wasm execution layer.

Do not equate CPU overhead with GPU overhead. Pass-profiled GPU timestamps showed larger Dawn deltas, but the measurement itself splits physical passes. Queue-drained native WGSL throughput was only +2.27% on x64 and -3.72% on ARM64 versus native D3D12. Whole-frame, uninstrumented correlation remains the safer headline gate.

4. What could improve in Dawn?

The highest-value work is reducing CPU cost while preserving WebGPU's safety contract. Some opportunities belong in Dawn; others require WebGPU specification extensions or engine-side discipline.

Highest impact

Reduce submit-path overhead

Profile validation, command-buffer finalization, descriptor realization, barrier generation, and backend queue submission. Cache invariant validation and batch native work without adding hidden queue drains.

High impact

Improve descriptor and state reuse

Reuse backend root signatures, descriptor allocations, bind-group translations, command allocators, and barrier plans more aggressively when immutable WebGPU objects repeat across frames.

Startup

Expose stronger persistent pipeline caches

Make backend pipeline cache identity, persistence, diagnostics, and asynchronous creation easier to control. Avoid repeating Tint/DXC/backend PSO work after a verified warm start.

Profiling

Make timestamps consistently usable

Native timestamp writes currently require an unsafe feature in the pinned Dawn package, while tested browsers advertise timestamp queries without exposing encoder writeTimestamp. A stable, portable capability contract would remove ambiguity.

Diagnostics

Provide phase-level telemetry

Expose low-overhead counters for validation, encoding, barrier synthesis, descriptor allocation, pipeline compilation, queue submission, and waits. Engines need attribution without wrapping every Dawn call and perturbing the result.

Windows presentation

Upstream immediate-mode tearing behavior

The project had to patch Dawn's DXGI present path to pass DXGI_PRESENT_ALLOW_TEARING for eligible immediate-mode swapchains. This behavior should be correct upstream and covered by a regression test.

Scheduling

Use backend queues more effectively

WebGPU intentionally exposes one logical queue, so public direct/compute/copy selection needs specification work. Dawn can still improve internal upload scheduling and overlap without changing observable ordering.

Reliability

Strengthen loss and recovery diagnostics

Provide clearer device-loss causes, object lifetime traces, in-flight work state, and recreation guidance. T850 now supports a configurable bounded recovery budget and native repeated-loss exhaustion testing; browser repeated-loss coverage and long-run leak accounting remain application responsibilities.

Evidence and limits

The accepted CPU matrix used scene 1, compute post-processing, fixed simulation, 1,800 profiled frames, frames 300-1799 analyzed, and three repetitions per backend. GPU matrices used five 600-frame held runs at 1920x1080. Results are specific to the tested x64 RTX 4080 Laptop and ARM64 Adreno X1-85 systems.
