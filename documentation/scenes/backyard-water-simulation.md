fixed, the tradeoffs, and the limits that remain.

## 3. Asset pipeline

All geometry is **parametric**, generated by script rather than hand-modelled, so a dimension
change cannot desync the mesh from the simulation.

### 3.1 Blender generator

[build_backyard.py](../../T850/scripts/blender/build_backyard.py) — run headless:

```
"C:\Program Files\Blender Foundation\Blender 5.1\blender-launcher.exe" \
  --background --factory-startup --python T850/scripts/blender/build_backyard.py
```

Emits: `Backyard_Ground.glb`, `Backyard_House.glb`, `Backyard_Pool.glb`,
`Backyard_Wall.glb`, `Backyard_Props.glb`, `Backyard_Water.glb`, plus
[backyard_layout.json](../../T850/Assets/Models/Backyard/backyard_layout.json).

Coordinate convention: Blender `(x, y, z)` maps to engine `(x, z, y)`.

Pool parameters (metres):

| Parameter | Value |
|---|---|
| Inner footprint X | −4.5 … +4.5 (9.0 wide) |
| Inner footprint Z | −9.0 … −4.5 (4.5 long) |
| Depth (floor Y) | −1.60 |
| Water plane Y | **−0.04** |
| Freeboard (air above water) | **0.42** |
| Wall thickness | 0.25 |
| Coping width / height | 0.40 / 0.08 |
| Steps | 3 (rise 0.30, run 0.35) at max X |

The pool mesh has **named nodes** so the solver can find boundaries by name rather than
guessing boxes: `Pool_Wall_XMin`, `Pool_Wall_XMax`, `Pool_Wall_YMin`, `Pool_Wall_YMax`,
`Pool_Floor`, `Pool_Step_1..3`, plus coping nodes.

The layout JSON carries, in addition to the authored geometry, two values the solver treats
as authoritative:

- `waterPlaneY` — the plane the water mesh is authored at. The solver derives its fill level
  from this so the still surface lands exactly on the mesh.
- `pool.freeboard` — metres of air kept above the water plane. **This was a real bug**: the
  original domain topped out 0.02 m above the water plane, under one cell of air, so the
  free surface had nowhere to rise and behaved like a solid lid.

### 3.2 Water mesh resolution

The water surface is authored as an explicit grid with exact UVs 0..1 across the pool
footprint (no smart-project), because the vertex shader samples the solver's height texture
by UV.

`nx = 288`, `nz = 144` vertices. That is deliberately **well above** the 100×50 solver grid:
storage textures cannot be sampled with hardware bilinear filtering, so the vertex shader
reconstructs bilinearly by hand, and it needs to *sample* that reconstruction at a finer
rate than the texture for the interpolation to be visible.

### 3.3 Ball generator

[build_ball.py](../../T850/scripts/models/build_ball.py) — writes glTF 2.0 binary directly
(no Blender dependency):

```
python T850/scripts/models/build_ball.py
```

Produces `Backyard_Ball.glb`: a unit-radius **spherified cube** (16×16 quads per face, 1734
verts, 3072 tris) at the origin with an identity transform. Each face carries a full 0..1 UV
square; the balls never rotate and the camera looks down, so a UV sphere's pinched pole would
sit where the viewer looks. The material declares base colour, normal and metallic-roughness
maps as embedded 1×1 PNGs (the old red rubber look) with every factor 1.0. Declaring them makes
the loader build the textured permutation and MikkTSpace tangents; at runtime each ball gets a
random palette set through `PrimitiveInst::InstanceMaterialMaps` (W-25,
`Scenes/BackyardBallMaterials.json`, textures `Textures/Ball/<id>/` from
`scripts/DownloadTextures.ps1`). Radius and placement come from the scene, not the asset.

### 3.4 Water normal map generator

[build_water_normal.py](../../T850/scripts/textures/build_water_normal.py) — writes
[WaterNormal.png](../../T850/Assets/Textures/Backyard/WaterNormal.png), 256² tiling normal
map.

**Tradeoff / correction:** the first version summed integer-frequency sine waves, which is a
poor spectrum. It was replaced with a **Phillips-style band-limited spectrum, 32,944
components**. The classic Phillips cutoff `g/U²` is metre-scale and rejects everything inside
a pool-sized tile, so a Gaussian band around a 12 cm peak wavelength with `k⁻²` falloff is
used instead, targeting a P99 slope of 0.42.

### 3.6 Cloud publishing for the meshes

Because the `.glb` files are not tracked, a checkout without the download step fails at load time
with `[SceneDescriptor] Cannot open 'Scenes/BackyardScene.json'` / `[glTF] cannot open
'Models/Backyard/*.glb'`. Measured on the Steam Deck on 2026-11-03: the branch built and ran but
scene 7 had no geometry until the meshes were installed.

Two R2 buckets and two manifests:

| Object | Bucket | Written by | Read by |
|---|---|---|---|
| `Backyard/*.glb` | `t850-models` | `scripts/PushCloudModels.ps1` | all four model downloaders |
| `runtime_assets.json` | `t850-models` | `scripts/PushCloudModels.ps1` | `DownloadModels.ps1`, the launcher, `steamdeck/DownloadCloudAssets.py`, Android `AssetDownloadActivity`, `web/cloud-assets.mjs` |
| `manifest.json` (union: models **and** textures) | both buckets, identical copies | `scripts/PushCloudTextures.ps1` | `DownloadTextures.ps1`, the web `TEXTURES` binding |

`runtime_assets.json` entries are `{key, url, size, sha256}` with `key` relative to `Assets/Models/`
— the contract every downloader implements. The union manifest keeps the same key convention for
model entries (`key: Backyard/Backyard_House.glb`, `localRelativePath:
Models/Backyard/Backyard_House.glb`).

```
# publish or update the Backyard meshes (dry run first, then -Apply)
pwsh scripts/PushCloudModels.ps1
pwsh scripts/PushCloudModels.ps1 -Apply
# -Check verifies the cloud manifest against the local files and exits non-zero on a gap
pwsh scripts/PushCloudModels.ps1 -Check

# keep the union manifest in step with the same meshes
pwsh scripts/PushCloudTextures.ps1 -Prefix Models/Backyard -Apply
```

Measured 2026-11-03: 7 meshes, 16.72 MB; `runtime_assets.json` 13 → 20 assets; the union manifest
218 assets (80 models, 138 textures) after the repair below. Every object was re-downloaded from
its public URL and matched its recorded sha256.

**Two bugs this exposed in the shared publishing scripts**, both fixed:

1. **The union manifest duplicated model entries on every run.** The merge lookup keyed on
   `$TexturesBucket` unconditionally, so a model file (bucket `t850-models`) never matched its
   existing entry and each run appended another copy; `Get-EntryIndex` then refused the following
   run with `Manifest has duplicate entry`. The lookup now uses the file's own bucket, the bucket
   and `kind` come from the prefix (`Models/…` → `model` → `t850-models`), and the prune filter no
   longer short-circuits on `kind -ne 'texture'` (it used to delete a pruned model's *object* while
   leaving its manifest entry pointing at nothing).
2. **`Test-PublicObject` reported every object as unserved on PowerShell 7.6**, because
   `$response.Headers['Content-Length']` is a `String[]` and casting it to `[int64]` throws; the
   throw was swallowed by the retry loop. This made a successful 16.72 MB upload look like a
   failure. Both scripts now parse the header explicitly.

`scripts/RepairCloudManifestDuplicates.ps1` is the one-off that removed the eight duplicate entries
those two bugs left in the live manifest (226 → 218 assets, `manifestVersion` 4 → 5, both buckets
byte-identical). It is kept because the failure is loud but not self-repairing.

## 4. Engine capability added: 3D compute storage textures

Before this work the engine had **zero** `Texture3D` / `image3D` support anywhere. A 3D
Navier–Stokes solver needs volumetric storage, so this was added to the abstraction and three
backends.

[BaseDriver.h](../../T850/Framework/include/video/BaseDriver.h) additions:

```cpp
enum class ComputeTextureDimension { Tex2D, Tex3D };

// ComputeBindingLayoutDesc gained:
ComputeTextureDimension dimension = ComputeTextureDimension::Tex2D;

struct ComputeTexture3DDesc {
  uint32_t width, height, depth;
  ComputeStorageFormat format = ComputeStorageFormat::Rgba16Float;
  ComputeBufferAccess access = ComputeBufferAccess::ReadWrite;
  std::string debugName;
};

class ComputeTexture3D { public: virtual ~ComputeTexture3D() = default;
  ComputeTexture3DDesc descriptor; };

// ComputeBindingDesc gained:
ComputeTexture3D* texture3D = nullptr;
// ...and later (97009aef) per-dispatch data for a ReadOnlyBuffer without a persistent buffer:
const void* inlineData = nullptr; uint32_t inlineBytes = 0, inlineStride = 0;

virtual bool SupportsComputeTextures3D() const { return false; }
virtual std::unique_ptr<ComputeTexture3D> CreateComputeTexture3D(
    const ComputeTexture3DDesc& desc, const void* initialData = nullptr) { ... }
```

Implemented in:

- `Framework/src/video/d3d11/D3D11Compute.cpp` + `include/video/d3d11/D3D11Compute.h`
- `Framework/src/video/d3d12/D3D12Compute.cpp` + `include/video/d3d12/D3D12Compute.h`
- `Framework/src/video/vulkan/VulkanCompute.cpp` + `include/video/vulkan/VulkanCompute.h`
- `Framework/src/video/gl/GLCompute.cpp` + `include/video/gl/GLCompute.h` (W-28, 2026-11-02):
  `glTexStorage3D` volumes, `glBindImageTexture` with `layered = GL_FALSE` (a `GL_TEXTURE_3D` is
  not an array texture, so the image unit always carries the whole level), 3D sampled binds that
  restore `GL_TEXTURE_BINDING_3D`, and inline `ReadOnlyBuffer` uploads into one persistent SSBO.
  The GLSL twins for it are generated by `scripts/shaders/generate_gl_compute_twins.ps1` and
  guarded by `scripts/validation/check_gl_twins.py`; see
  `documentation/rendering/compute-shader-implementation.md` for the flags that matter.

Plus driver headers (`D3D11Driver.h`, `D3D12Driver.h`, `VulkanDriver.h`, `GLDriver.h`) and
`Framework/src/video/BaseDriver.cpp` for shared binding validation.

### Critical discovered constraints

1. **Storage images are write-only on Vulkan.** `SPV_REFLECT_DECORATION_NON_READABLE` must be
   *set*, and the SPIR-V needs `[[spv::nonreadable]]` plus the format (`[[spv::format_rgba16f]]`,
   or `[[spv::format_r32f]]` for the scalar fields). Consequence:
   **every field needs ping-pong** — no in-place updates anywhere in the solver.
2. **Originally only `RGBA8` and `RGBA16F` storage formats existed**, so scalars were packed into
   `.x` of an RGBA16F volume. Since W-02 (`14c705f4` format, then the switch) `R32Float` exists
   on D3D11/D3D12/Vulkan/GL; α, pressure and divergence are R32F and velocity stays RGBA16F.
   Readers still declare `Texture3D<float4>` and read `.x`: an R32F view returns `(r, 0, 0, 1)`.
3. Storage textures cannot be hardware-filtered — all reconstruction is manual (see §9.5).

## 5. Kernel registry

[compute_kernels.json](../../T850/Assets/Shaders/compute_kernels.json) is the single source of
truth for kernel bindings. A kernel exists only if registered here; an unregistered kernel is
silently skipped.

**Important:** `constant_count` must exactly match what the shader reflector reports. It is
easy to get this wrong:

- A cbuffer declared with **two floats** is padded to **four DWORDs**, so `constant_count`
  must be `4`, not `2`. The divergence between declared and reflected counts makes the driver
  **silently reject the pipeline** (no error logged) — this cost significant debugging time.
- `constant_count: 16` for the 64-byte `FluidConstants` (4×uint + 12×float).

The fluid kernels below are the original set. Later additions, each with its exact binding list
in `compute_kernels.json`: `fluid_extrapolate` (air-velocity extrapolation), `fluid_surface_to_buffer`
(surface readback), `fluid_volume_reduce` (`CS_FluidVolumeReduce3D`: GPU sums for the volume
correction, §10), `fluid_stamp_bodies` (`CS_FluidStampBodies3D`: bodies stamped into the
wall mask on the GPU, §8.3) and `fluid_body_level` (`CS_FluidBodyLevel.hlsl`: the body's water
line sampled from the surface, §8.1). `fluid_volume_correct` now also binds the sums buffer
(`read_write_buffer:1@4`), and the body kernels bind `BodyVelocity` at t9 as an inline buffer.
`FluidConstants` is now 20 DWORDs (`constant_count: 20`, open-ceiling fields added).
`fluid_sphere` (`CS_FluidSphere3D`) is no longer registered or loaded; the body is a wall-mask
solid plus `CS_FluidObstacleVelocity3D`. Since W-02 the storage binding of `fluid_divergence`,
`fluid_pressure`, `fluid_seed_alpha`, `fluid_alpha_advect` and `fluid_volume_correct` declares
`r32float`, and `fluid_clear_float` (`CS_FluidClearFloat3D`) clears those volumes on reset; the
storage format is part of the binding, so `fluid_clear` cannot serve both.

## 6. Solver architecture

[FluidSimulation.h](../../T850/Framework/include/simulation/FluidSimulation.h) and
[FluidSimulation.cpp](../../T850/Framework/src/simulation/FluidSimulation.cpp) are the host
side. All GPU state is owned by the solver; the scene only supplies tunables and a surface
render target.

### 6.1 Domain and units

Engine space, metres. The solver domain is exactly the inner basin:

| | From | To | Cells |
|---|---|---|---|
| X | −4.50 | +4.50 | 100 |
| Y | −1.60 (floor) | 0.38 (water plane −0.04 + freeboard 0.42) | 22 |
| Z | −9.00 | −4.50 | 50 |

Cell size 0.09 m. Domain height is exactly `Height × cellSize` so the column integral in the
surface kernel converts to metres without a scale error.

Water volume is represented as a **volume fraction α ∈ [0,1]** per voxel: 1 = water, 0 = air,
fractional at the interface. Seed fill 78.8% → **72,970 alpha cells** of 94,923 fluid voxels
(110,000 total, 15,077 solid from the geometry mask).

Shallow-water wave speed √(g·h) ≈ 3.9 m/s ≈ 43 cells/s, i.e. ~0.9 cells/frame at 60 fps — the
grid can carry a gravity wave.

### 6.2 Per-frame order

```
Step(frameDt):
  substeps = clamp(ceil(bodyTravel / (0.5 * cellSize)), 1, 12)     // §8.3
  subDt    = frameDt / substeps
  for each substep: StepInternal()

StepInternal():                    // m_settings.deltaTime == subDt
  m_time += dt
  AdvanceSphere(dt)                // body integration
  UpdateWallMaskForBody(driver)    // body becomes solid for everything
  advect velocity (semi-Lagrangian)
  forces + viscosity
  StepObjectVelocity(driver)       // no-penetration at the moving body
  divergence (wet cells only)
  60 × red-black Gauss-Seidel + SOR 1.8   (2 dispatches per sweep)
  gradient subtraction + no-penetration clamp
  advect alpha (flux form, conservative)
  air rise (vertical drift flux, conservative; airRiseSpeed 0.25 m/s)   // W-29
  clear body footprint (via the wall mask, not a separate pass)
  last substep only: derive 2D surface texture (ping-pong), copy to the stable output target
after the substeps, every volumeCheckInterval (15) frames: CorrectVolumeFraction
  (two dispatches, no readback: §10)
```

The ordering is load-bearing:

- `AdvanceSphere` and `UpdateWallMaskForBody` run first so every later stage sees the same
  body configuration.
- `StepObjectVelocity` runs **after forces and before divergence**. After projection would be
  undone by the gradient subtraction.
- Alpha is advected **after projection**, so the flux field is the one the fluid actually
  moves with.

### 6.3 Kernel by kernel

**`CS_FluidAdvect3D`** — semi-Lagrangian velocity self-advection.

**`CS_FluidForces3D`** — viscous diffusion from six neighbours, plus gravity, plus wind, plus
(optional, default off) a synthetic surface stir. Wind (W-27) is a surface stress
`τ = ρ_air · 1.3e-3 · |U| U` (U in m/s, `windX`/`windZ`) applied as `τ / (ρ_water · h)` to the
one horizontal face per column that is wet with air above it, found from α (bound at t2). It
used to be multiplied by `ForcingAmplitude` (0 in the shipped scene), so wind did nothing. At the
shipped 0.7 m/s it is negligible; 10 m/s along X builds about 6 mm/s of surface current in 20 s.
Ends with `velocity *= saturate(1 - Damping*dt)` and `clamp(velocity, ±12)`.

**`CS_FluidDivergence3D`** — central-difference divergence with `scale = 0.5/CellSize`.
Solid neighbours contribute zero flux (wall no-penetration via the mask). Air cells get
divergence = 0.

**`CS_FluidPressure3D`** — one red-black Gauss-Seidel pass with SOR. Parity is packed into
`Iteration`, ω into `Padding0`. Because storage textures are write-only, an in-place
Gauss-Seidel is impossible: the ping-pong pair carries the intermediate field and cells of the
other colour are copied through. Boundaries:
- **Dirichlet p = 0 at air** — this makes the pressure matrix non-singular, so **no mean
  removal is needed**.
- **Neumann at solid** (`PressureAt` returns the centre pressure for solid neighbours).

**`CS_FluidGradient3D`** — `u -= ∇p`, then a per-face no-penetration clamp: a velocity
component pointing into a solid neighbour is zeroed. Air velocity is deliberately **not**
zeroed (see §7 bugs).

**`CS_FluidSurface3D`** — derives the renderable 2D surface from the volume fraction. See §7.

**`CS_FluidDiagnostics3D`** — reduces speed/divergence statistics to a buffer for readback. The
buffer is persistent (allocated once, not per call), so the kernel clears its own two `uint4`
counters from thread (0,0,0) when `Iteration == 0xFFFFFFFF`, dispatched as a pass before the
measuring one — there is no buffer-write API to do it from the host.

**`CS_FluidCopy3D`** — volume→buffer readback copy.

**`CS_FluidSeed3D` / `CS_FluidSeedAlpha3D`** — initial velocity and initial volume fraction.

**`CS_FluidAlphaAdvect3D`** — flux-form conservative transport. See §6.5.

**`CS_FluidAirRise3D`** — entrained air rises back out (W-29). The solver is single-phase with no
bubble buoyancy, so air a splash pushes under the surface used to stay there for good. Across
every face between two open cells, water moves down and air up by
`F = c (1 − α_lower) α_upper`, `c = airRiseSpeed · dt / h ≤ 1`. Both cells read the same two
values, so each column's water total is conserved exactly, and with `c ≤ 1` every cell stays in
[0, 1] without a limiter. Fully wet or dry columns and a sharp interface carry no flux; a smeared
interface is pulled back to a step, which does not change a column's total, so the drawn surface
is unchanged. Air under a solid (a step, a floating body) stays. Measured over 30 s after the
default drop: bulk cells below 98 % α 3614 → 24 (the 24 are under solids), interface 3.36 → 1.16
cells. Every gate passes from 0.1 to 0.5 m/s; 0.25 ships (`airRiseSpeed` in the water JSON, a
slider in the GUI, `--backyard-air-rise` for the self-test).

**`CS_FluidVolumeCorrect3D`** — global mass correction. See §10.

**`CS_FluidVolumeReduce3D`** — sums total α, interface headroom and interface α for the
correction, on the GPU. See §10.

**`CS_FluidStampBodies3D`** — rewrites the wall mask from the static base mask plus the body
list. See §8.3.

**`CS_FluidBodyLevel`** — one thread per body walks the columns of an annulus around that body and
averages the surface height and the horizontal liquid velocity at the shallower of the column's
waterline row and the body's centre row. Bodies come in as an inline `(x, y, z, radius)` list
(radius 0 for a disabled body); the result is one `float4` per body (mean level offset, current x,
current z, sample count), so every ball is answered by one dispatch and one readback. Feeds the
buoyancy water line (level) and the drag reference (current) in §8.1; the host reads it back
asynchronously one to three frames later.

### 6.4 Pressure solve maths

Consistent discrete projection:

$$\nabla^2 p = \nabla\cdot u,\qquad u \leftarrow u - \nabla p$$

with `pressureScale = h²`. The two conventions (`∇²p = div` with `u -= ∇p`, versus
`∇²p' = div/dt` with `u -= dt∇p'`) must not be mixed: mixing them over-corrects by `1/dt` and
makes divergence *grow* with iteration count. This was one of the earliest bugs.

Red-black Gauss-Seidel with ω = 1.8 converges in 60 sweeps over this domain, measured residuals
0.974 / 0.616 / 0.436 at 1/8/50 sweeps.

### 6.5 Conservative volume-fraction transport

`CS_FluidAlphaAdvect3D` is written in flux form so that every face flux leaving one cell
enters its neighbour, and summing over the domain telescopes to boundary fluxes only.

One kernel, no intermediate flux texture: each cell reads its six neighbours and the six
collocated face velocities (`0.5 * (u_cell + u_neighbour)`), then integrates the net flux
inline.

Compression is a Russo–Smereka term:

```
flux += alphaCompression * abs(faceVelocity) * (alphaCell - alphaNeighbour)
```

Three bugs were found here (see §14): a one-sided compression sign that created mass,
clamping that destroyed mass, and zeroing air velocity in the gradient.

## 7. Surface derivation and the texture contract

`CS_FluidSurface3D` writes one texel per water column (100 × 50):

| Channel | Meaning |
|---|---|
| **R** | surface height as a **DELTA from the authored water plane**, metres |
| **G** | foam |
| **B** | slope dH/dx as a per-texel height **difference** (not divided by spacing) |
| **A** | slope dH/dz |

**The contract is subtle and three bugs hung off it:**

1. **R must be a delta**, because the water mesh already sits at the authored plane and the
   vertex shader *adds* R. Writing an absolute elevation dropped the surface by the full depth.
2. **Slopes are per-texel differences**, not gradients. The fragment shader multiplies by
   `2/cellSize` (the stencil spans two cells). Dividing in the kernel would double-apply the
   conversion.
3. **Wall columns must report the water plane**, not the basin floor. Reporting the floor
   dragged the water mesh's edge vertices down the whole depth. A probe caught this: texel
   (0,0) reported −1.5596.

Elevation is the column integral of α:

```
water     = sum of alpha over the open rows (solids under wet water count as full)
elevation = BasinMinY + water * CellSize
```

From W-02 to W-29 the kernel also counted air more than two cells below the integral surface as
volume, because the solver could not move entrained air and it drew a 1.7–3 cm moat round a
floating ball. That term turned every leftover air pocket into a fixed bump: after a splash the
water stopped moving but the surface stayed wavy (±2 cm) and the mean crept up by centimetres
per half hour. `CS_FluidAirRise3D` now lets the air leave, and with the term removed gate 7 reads
`covered min−ring` −2.2 mm (it was −11.3 mm with the term and trapped air).

A column with no water is a wall column and reports the water plane, contributing zero delta.

### 7.1 Tent reconstruction

The raw column integral changes in whole-cell steps as the interface cell fills, so the raw
elevation is staircase-quantised on 0.09 m cells and read as blocks at the water edge.

A separable 3×3 tent (weights 1,2,1 / 16) is applied to the 3×3 neighbourhood of column
elevations **before** the slopes are taken, so the normal cannot disagree with the surface.
Each 8×8 thread group integrates its 10×10 neighbourhood of columns once into `groupshared`
memory and the tent reads from there. It used to call `ColumnElevation` per tap, 9 times per
texel, and a column next to a body also walks up to 64 neighbouring columns to inpaint, so the
kernel cost 0.5–1 ms a frame; the tiled version made scene 7 run 306.8 → 415.3 fps (D3D12) and
353.4 → 402.3 fps (Vulkan) at 720p with no spawned balls, and 266.7 → 377.0 / 327.2 → 360.2 fps
with 30, same session, together with the R32F switch.

Note this also fixed a factor-of-2 error: the shader multiplies slope by `2/cellSize`, and the
tent-weighted difference is (1/4)·Δ rather than (1/2)·Δ, so the two combine to the correct
gradient. The pre-tent formulation was 2× over-amplified.

### 7.2 Data-driven constants

`T8_BASIN_MIN_Y` and `T8_WATER_PLANE_Y` used to be `#define`d literals in the kernel. They are
now a `cbuffer GeometryConstants : register(b1)` filled from the pool layout JSON
(`BasinMinY`, `WaterPlaneY`, `WorldOriginX`, `WorldOriginZ`). The sphere kernel likewise takes
`BasinMinY` and the grid origin as constants.

## 8. The dropped body

A rigid sphere dropped into the pool. Two mechanisms couple it to the fluid, and **both are
required** — each alone was tried and failed:

1. **Solid boundary.** Each frame the body's voxels are stamped into the wall mask, so
   divergence, pressure, gradient and alpha advection all treat it as solid. Before this the
   pressure projection simply undid whatever velocity the body imposed, because the sphere was
   invisible to it.
2. **Momentum source.** `CS_FluidObstacleVelocity3D` imposes the no-penetration condition at a
   moving boundary:

$$u\cdot n = u_\text{body}\cdot n$$

   on fluid cells within `radius + 1.5·cellSize` of the body centre, weighted to zero across
   that band, applied only to wet cells. Only the normal component is touched; the tangential
   component is left alone, matching the free-slip convention used at the pool walls.

Without (2) there is no divergence from the impact, so the pressure solve has nothing to react
to and **no wave can radiate**. Without (1) the projection cancels (2).

### 8.1 Body integration (`AdvanceSphere`)

Submerged fraction from the water line the body floats on — the **simulated** surface sampled
around the body (W-06), not the authored plane:

```
level     = waterPlaneY + mean(surface height over an annulus around the body)
submerged = clamp((level - (y - radius)) / (2*radius), 0, 1)
```

`CS_FluidBodyLevel.hlsl` produces that mean on the GPU for every body at once: it averages
`m_surfaceOutput` over an annulus whose inner radius (1.05 r) clears the body's own meniscus and
whose outer radius (2 r + h) stays inside the next body, skipping columns whose waterline cell is
a wall or another body. The result comes back through the asynchronous readback (W-04 step 5) one
to three frames late with one query in flight; each body keeps its last answer, and an answer is
dropped if bodies were spawned or cleared since it was requested. A backend without an async path
pays one small stall per frame instead of losing the coupling. The surface texture stores a delta
from the authored plane, so the plane is added back; forgetting that puts the body on the pool
floor. Headless runs (no bound surface output, i.e. the self-tests) keep the authored plane.

Archimedes, net of gravity:

$$a_\text{net} = g\left(\frac{\text{submerged}}{\rho_\text{rel}} - 1\right)$$

Equilibrium is `submerged = ρ_rel`, which is why **density alone** decides floating depth and
mass does not enter this term. Because the level now follows the surface, a body rides a crest and
drops into a trough; `sphereHeaveDamping` (0.15) is the remaining hand-tuned stand-in for the
energy it should radiate as waves.

**The heave damping is measured, not fitted.** With the coupling still one-way nothing radiates the
body's heave energy away, so the ratio is the only sink. Scene 7, settled window t = 5…10 s
(`--backyard-ball-probe 30`): 0.15 → **18 mm** residual bob (max |vy| 0.050 m/s), 0.05 → 128 mm
(0.365), 0.00 → 307 mm (0.875). The sampled level stays inside 4 mm of the plane over that window,
so the 18 mm is the body following real surface motion rather than a free oscillation, and 0.15 sits
inside the 0.1–0.3 band a real heaving sphere radiates at. Two-way coupling (W-07) is what would let
it come down.

**Trapped air.** Air a plunge pushes beside the ball used to stay there and read as missing water
(a moat), which the surface kernel hid with a trapped-air term. Since W-29 the air rises out
(`CS_FluidAirRise3D`) and the term is gone: `ring−far` −1.6 mm, `covered min−ring` −2.2 mm on
D3D12 (−2.0 / −15.9 mm before).

Quadratic drag **with added mass**, acting on the velocity *relative to the local current*:

$$F_d = \tfrac12 \rho_w C_d A v_\text{rel}^2,\qquad
m_\text{eff} = \rho_w V\left(\rho_\text{rel} + \tfrac13\right),\qquad
a_\text{drag} = \frac{9\,C_d\,v_\text{rel}^2}{16\,r\left(\rho_\text{rel} + \tfrac13\right)}$$

where $v_\text{rel} = v - u$ and $u$ is the annulus mean horizontal velocity from the same kernel
that supplies the level. The update solves for the relative velocity and adds the current back
($v = u + (v-u)/(1 + \tfrac{a_\text{drag}}{|v_\text{rel}|}\Delta t)$), so a current carries the body
instead of the water being an absolute brake. Measured direction check: with $u$ forced to
(+0.5, −0.25) the body ends at the +X and −Z walls.

The added-mass term is `½ ρ_w (2/3)πr³` — the water the body drags along. Dividing by the
*effective* inertia is what makes a dense body punch through the surface while a light one is
stopped dead. Integrated explicitly with `dragStep = min(a_drag/|v| * dt, 0.5)` so a fast entry
cannot reverse velocity in one frame.

Floor and wall clamps apply `restitution` (default 0.30) rather than a dead stop.

**This replaced** a hardcoded `v *= 1/(1 + 6·|v|·dt)`, which was mass-independent and about 5×
too strong at entry speed.

### 8.2 Substepping (`Step`)

The body is only sampled at discrete instants — its voxels stamped and its velocity imposed
once per (sub)step. Above `cellSize/dt` (**5.4 m/s** at 60 fps, 0.09 m cells) the body crosses
more than a cell per frame and **jumps clean over the water in between**: the fluid never learns
it was there.

`Step()` therefore subdivides the frame so the body's displacement stays under **half a cell**
per substep (capped at 12):

```
substeps = clamp(ceil(|v| * frameDt / (0.5 * cellSize)), 1, 12)
```

Each substep runs the whole pipeline with `dt/substeps`. This keeps the stamp, coupling,
divergence, pressure, gradient and advection mutually consistent, and also keeps the flux-form
alpha advection inside its CFL limit. The frame delta is restored afterwards so the GUI sees
real values. A `T8_LOG_DEBUG` line reports `substeps`, `bodySpeed` and `travel`.

### 8.3 Wall mask stamping (`UpdateWallMaskForBody`)

The authored mask lives in two places: `m_baseMask` on the CPU and `m_baseMaskBuffer` on the
GPU (static). The live mask `m_wallMask` is a persistent **read-write** buffer that every
kernel binds read-only at t8. Every body is stamped as `2u + k` (static solids stay 1), so the
body kernels can look up that body's velocity:

- Each substep computes every enabled body's cell footprint. When all footprints and the body
  count match the previous substep, nothing happens.
- Otherwise `CS_FluidStampBodies3D` rewrites the whole mask in one dispatch from the base mask
  plus an inline list of `(x, y, z, radius)` per body: cell centre inside a sphere → `2 + k`,
  later bodies win on overlap, authored solids untouched (the same rules as the CPU stamp).
- The CPU stamp (copy the base mask, stamp, re-create the buffer) is kept only as a fallback
  when the GPU path is unavailable. It used to run on every footprint change and its blocking
  re-upload stalled the frame for ~10 ms while a ball moved (W-15 P6, fixed in `c911381a`).

Making the body solid in the mask is what clears its footprint from the alpha field: the
advection kernel writes solid cells to zero, so no separate removal pass is needed.

### 8.3.1 Picking and dragging a body

Ctrl + left click picks a ball (see `documentation/input/camera-and-controls.md`, "Backyard").
`FluidSphere::held = true` makes `AdvanceOneSphere` skip gravity, buoyancy, heave damping and
drag, so the velocity the scene sets each frame (toward the cursor target, capped at 6 m/s, and
clamped to the basin) is what moves it. `ResolveBodyContacts` gives a held body zero inverse
mass, so it pushes other balls without being pushed. Releasing clears `held` and keeps the last
velocity, which throws the ball. Clearing balls, rebuilding the solver and destroying the scene
all release a held body first.

### 8.4 Reset (`ResetToRest`)

`CS_FluidClear3D.hlsl` zeroes the RGBA16F velocity volumes and `CS_FluidClearFloat3D.hlsl` the
R32F scalar ones. Reset clears:
- both velocity volumes, both pressure volumes, the divergence volume, both alpha volumes
- `m_current`, `m_pressureCurrent`, `m_time`, the volume-check counter
- `m_maskBodyValid` so the body footprint is re-stamped cleanly

then re-seeds the volume fraction and re-locks the reference mass, and the scene re-arms the
body at the configured height with `enabled = false` so the release delay applies again.

**Clearing momentum is the point**: without it the next drop lands in water the previous one
set moving, and two runs at different heights are not comparable. Body parameters are
deliberately **not** reset.

## 9. Rendering

The water is a single forward-pass mesh with the `FLUID_SURFACE` permutation selected by
`PrimitiveInst::PersistentFeatureBits`.

### 9.1 Water shading

[FS_Mesh.hlsl](../../T850/Assets/Shaders/FS_Mesh.hlsl) — layered water, Crysis-style:

1. **Beer–Lambert absorption** from path length. Crucially the path length is
   **view-independent**: `columnDepth / cosθ` derived from the *simulated* elevation. A
   camera-height-dependent formula produced dark patches that slid across the surface as the
   camera moved — the first "screen-space artifact" report.
2. **Refraction** of `SceneColorTex` by the surface normal, with a border fade so the pool edge
   cannot sample outside the surface.
3. **Caustics** driven by the *simulated* slope, floor-base lifted so the pool bottom is not
   pitch black.
4. **Reflection**: mip-0 sky/IBL reflection + GGX + sun glint, plus screen-space reflections
   (§9.2).
5. **Fresnel** computed from the **macro** normal, not the rippled normal. Rough-surface
   Fresnel averages over microfacets; using the rippled normal produced dark patches.
6. **Foam**, border-gated, from velocity divergence.
7. **Volumetric scattering** term.

Shader-side slope → normal:

```hlsl
float fluidCellSize = max(WaterMisc1.z, 0.001f);
float2 heightGradient = fluidSurface.zw * (2.0f / fluidCellSize);
heightGradient *= max(WaterMisc1.y, 0.0f);           // normalStrength
heightGradient = clamp(heightGradient, -4.0f, 4.0f); // see §9.5
normal = normalize(float3(-heightGradient.x, 1.0f, -heightGradient.y));
```

### 9.2 Screen-space reflections

SSR marches the reflected ray in screen space and compares NDC depths against `SceneDepthTex`.
`CameraVP` was added to the frame constant buffer for this.

Bugs fixed:
- self-intersection at the ray start
- Y-handover detection (the projected y must reverse direction at a hit)
- a depth-residual weight that behaved differently per backend
- added a 5-tap blur

**Prerequisite:** the water must not write GBuffer depth, or `SceneDepthTex` would contain the
water itself and SSR would have nothing behind it to trace against. This drove
`PrimitiveInst::DrawPassMask`:

```cpp
instance.DrawPassMask = ~((1ull << PassType::GBUFFER) | (1ull << PassType::SHADOW_MAP));
```

### 9.3 Normal map and procedural layers

A fabricated tiling normal map plus 6 analytic ripple octaves exist, but are **off by default**
(`fakeRipplesEnabled = false`). They were the original stand-in for a simulation; now that the
solver drives the surface they only add noise on top.

**Gotcha:** `[unroll] for` over a local `const` array silently collapsed every octave onto
element 0. Octaves are macro-expanded instead.

### 9.4 Vertex displacement

[VS_Mesh.hlsl](../../T850/Assets/Shaders/VS_Mesh.hlsl):

```hlsl
// Bilinear reconstruction: storage textures are not filterable.
float2 gridPos = fluidUV * float2(fluidWidth, fluidHeight) - 0.5f;
int2 base = clamp(int2(floor(gridPos)), int2(0,0), dims-2);
float2 frac = saturate(gridPos - float2(base));
float h = lerp(lerp(h00, h10, frac.x), lerp(h01, h11, frac.x), frac.y);
input.position.y += h * TimeParams.z;   // displacementScale
```

`displacementScale` is **1.0** — physically exact. It used to be **12**, chosen to make a
sub-millimetre analytic ripple visible; once the surface came from the real solver that
amplification turned every feature into a crater.

### 9.5 The "flashing surface" fix

**Symptom:** real waves appeared, but the surface flashed like noise frame to frame. The old
analytic version had looked fine.

**Cause:** the geometry was displaced with a bilinearly blended height, while the fragment
shader picked a **single nearest texel** for normal and foam. One texel covers several screen
pixels, so those blocks swept across the screen as the waves moved — a pixel's normal jumped
discontinuously at each block boundary and the specular lobe flicked on and off. The two stages
didn't even use the same texel-centre convention.

**Fix:**
- Fragment-side **bilinear reconstruction of all four channels**, using the identical
  texel-centre convention as the vertex shader.
- **Slopes are interpolated, not recomputed** from interpolated heights: the surface kernel
  already produces them from a tent-smoothed elevation, and differencing an interpolated height
  would filter twice and flatten the waves.
- **Foam averaged over three columns**, sharing the surface row so it costs only three extra
  fetches. Divergence is a second derivative and very spiky per cell; single-cell pops read as
  flashing whitecaps.
- **Slope clamped to ±4.** A pool wave is never steeper than a few degrees, so anything beyond
  is numerical noise, and an unbounded gradient fed a wildly wrong normal into the specular and
  reflection terms.

### 9.6 Constant buffer layout

Water look values ride to the shader in the tail of `MeshMaterialCBuffer` as **24 float4
groups**: `WaterOptics0..5`, `WaterWaves0..2`, `WaterReflect0..2`, `WaterFoam0..3`,
`WaterRipple0..5`, `WaterMisc0..1`. C++ (`WaterGpuParams` in WaterTunables.h) and HLSL
(`MeshMaterialCB`) declare identical names so the layout is checkable by eye.

`RenderMesh::Draw` binds textures via **per-slot `if` branches** with no generic loop. Adding a
new slot requires adding a branch — the solver's surface texture at slot **t23** was bound this
way, and the missing branch was one of the root causes of the water never moving (§14).

`RenderMesh` pre-compiles permutations only from the material key, for passes
FORWARD/GBUFFER/SHADOW_MAP/RADIAL_DEPTH. Draw-time flags like `FLUID_SURFACE` need an explicit
`driver->CreateShader()`.

## 10. Mass conservation

Two mechanisms:

**1. Conservative transport.** Flux-form advection, with antisymmetric compression, is
conservative up to the clamping that keeps α in [0,1].

**2. Global correction.** `CorrectVolumeFraction` runs every `volumeCheckInterval` frames
(default 15) and never leaves the GPU (`c911381a`):

1. `CS_FluidVolumeReduce3D` sums total α, interface headroom `Σ(1 − α)` and interface α over
   the band `[0.5, 0.999)` into a 4×`uint4` buffer: group-shared tree reduction, then one
   fixed-point atomic per group (whole cells + 1/65536 fractions, so 32-bit atomics neither
   overflow nor lose sub-cell precision). Two sum slots alternate.
2. `CS_FluidVolumeCorrect3D` reads its slot, computes `deficit = reference − total` and the
   same guards the CPU used to apply (|deficit| ≤ 0.5, no headroom to add into, no interface
   water to take from), applies the correction, and clears the other slot for the next round.

The CPU only supplies `reference` (below), which it knows without reading anything back. The
old path copied the whole α volume to the CPU and summed it, a full stall that showed as one
10–15 ms frame every 15 frames. At `--logLevel debug` the 64-byte sums are read back for a log
line; that is the only readback left.

The original correction rescaled interface cells multiplicatively:

```
alpha_out = saturate(alpha * scale)
```

This **cannot work**: interface cells sit just under 1, so `alpha * 1.03` lands above 1 and
`saturate()` discards the entire gain. Measured drift stayed at *exactly* the same value for 400
frames. It was replaced with an **additive, headroom-weighted** distribution:

```
corrected = saturate(alpha + deficit * (1 - alpha) / totalInterfaceHeadroom)
```

This puts the water where it can actually be stored, and every cell gains at least one half-float
ULP of change.

**Reference target with a body present.** Chasing the seed-time total while a ball sits in the
water made the correction pump water straight back into the cavity. Measured column elevations
formed an **18 cm dome centred on the ball** and the cavity never survived long enough to launch
a wave. The reference now subtracts the body's displaced volume:

```
reference = seedTotal - ballVolumeInCells * submergedFraction
```

Measured result: **5450 → 5450, drift 0.00%** on the synthetic test; 72,970 seeds in the pool
with drift −0.05% over 1200 frames without a body.

**How many pressure sweeps actually run.** `EffectivePressureIterations()` is the single source of
truth, and both the scene and the headless gates call it, so the gates validate what ships:

| Platform | Sweeps | Why |
|---|---|---|
| Desktop Windows (D3D11/D3D12/Vulkan/WebGPU/GL) | 120 (whatever the JSON says) | CPU and GPU headroom |
| Steam Deck (Vulkan) | 60 | Owner decision 2026-11-02; detected at run time |
| Android, Emscripten | 60 | Compile-time cap (`kMobilePressureIterations`) |

The Deck is a Linux build, so its cap has to be a run-time check — a compile-time `OS_LINUX`
branch would also cap a desktop Linux session. The probe lives in
[utils/DeviceInfo](../../T850/Framework/include/utils/DeviceInfo.h) and is shared with the input
layer; the Deck OLED identifies itself as `Valve` + `Galileo` (the LCD as `Valve` + `Jupiter`), and
before the probe knew that it logged `Handheld detection: no` and ran the desktop sweep count. The
scene logs the reason next to the number: `120 pressure iterations` on desktop,
`60 pressure iterations (Steam Deck cap)` on the Deck, `(mobile/web cap)` on devices.

Approximately 90 sliders in the ImGui dev GUI, grouped into sections: Solver, Optics, Surface
detail, Reflection, Ripple octaves, Foam, Dropped sphere, Presentation. Values apply live.

**Derived values are written back into the tunables.** Two separate bugs came from *not* doing
this:

- The solver derives its grid height (22) from the pool layout, but `SceneProp.Water.gridHeight`
  stayed at its literal default (18). `OnUpdate` rebuilds the solver whenever the requested grid
  differs from the applied one, so **it rebuilt and re-seeded every single frame** — the
  simulation could never accumulate. Verified: seeds went from 61-per-61-frames to 1.
- The same for `surfaceLevel`: `LoadPoolLayout` derives 0.788 from the water plane, but
  `SetSurfaceLevel` re-imposed the literal 0.96, so a reset re-seeded the pool at 96% fill.

Both derived values are now written back into the tunables after `TryInitialize`.

## 14. Root-cause log (bugs found and fixed)

This list is the most useful part of the document: most of these produced *silent* wrong
behaviour, not errors.

### Compute layer
1. **Storage images must be declared non-readable on Vulkan.** Missing
   `[[spv::nonreadable]]` / `[[spv::format_rgba16f]]` broke storage image creation.
2. **No `R32F` storage format** (fixed by W-02). Scalars lived in `.x` of RGBA16F, and fp16 α
   lost 0.69 % of a still pool in 2 s while diluting the bulk by 0.55 cells per column; R32F
   loses 0.001 %.
3. **`constant_count` mismatches silently reject pipelines.** A 2-float cbuffer reflects as 4
   DWORDs. Declaring 2 makes the driver return null with **no diagnostic**.
4. **`ComputeBuffer` has no update path.** A buffer created with seed data is immutable in
   practice. This silently froze the obstacle parameters (`enabled` read as 0 forever) and made
   the whole body coupling a no-op. Fixed by passing parameters as **constants**, which are
   re-uploaded every dispatch.
5. **`ReadComputeBuffer` inside the frame stalls the pipeline**, and one readback came back
   zeroed, silently no-op'ing a whole pass. Replaced with a GPU reduction (`fluid_sphere` totals).
5a. **OpenGL: `glBindImageTexture` needs `layered = GL_FALSE` for a volume.** `layered` only
   applies to array textures; a `GL_TEXTURE_3D` image unit always carries the whole level. (The
   stage plan said `GL_TRUE`; the Khronos reference says otherwise.) W-28.
5b. **OpenGL: NVIDIA rejects a writable unsized SSBO array indexed by a loop variable**
   (`error C5025: lvalue in array access too complex`). `CS_FluidDiagnostics3D`'s accumulator
   clear was a `for` loop and the program failed to **link** — not to compile, so the failure only
   showed up as `Solver resources are incomplete`. Now eight explicit stores. W-28.
5c. **OpenGL: a `const` initializer must be a constant expression.** `const int stepCount =
   int(WaterMisc0.x);` is legal HLSL and `C1059` in GLSL. W-28.
5d. **OpenGL: a non-base permutation needs its own twin file.** The loader used to replace the
   extension of `debugName`, which both dropped the `#divergent` suffix (`CS_FluidSeed3D.hlsl
   #divergent` → `CS_FluidSeed3D.glsl`) and demanded a per-permutation file from the hand-written
   twins that express permutations with `#ifdef`. `LoadComputeSource` now tries
   `<stem>.<permutation>.glsl` and falls back to `<stem>.glsl`. W-28.

### Solver physics
6. **Mixed projection conventions** (`∇²p = div` with `u -= ∇p` vs `∇²p' = div/dt`) over-corrected
   by `1/dt` and made divergence *grow* with iterations.
7. **A solid ceiling.** With no air above the water, a free surface is impossible. The top row
   must stay open.
8. **Zeroing air velocity in the gradient** made the free surface a solid lid; water pushed down
   had nowhere to rise and alpha clamping destroyed **27.7%** of the mass in 600 frames.
9. **One-sided compression sign** in the α flux created **4.5%** mass.
10. **Multiplicative volume correction cannot work** — `saturate(alpha * 1.03)` throws the whole
    gain away (see §10).
11. **Volume correction fighting the body** — chasing the seed total refilled the cavity and made
    an 18 cm dome centred on the ball (see §10).
12. **`[unroll] for` over a local `const` array collapses onto element 0** — all 6 ripple octaves
    evaluated at index 0. Macro expansion required.
13. **Fresnel from the rippled normal** produced dark patches; must use the macro normal.

### Scene / host
14. **Solver rebuilt and re-seeded every frame** because the derived grid height never matched the
    tunable default (61 seeds in 61 frames → 1 after the fix). This was *the* reason the water
    never moved.
15. **Stale `Framework.pch`** from a different MSVC toolchain caused `C2011` header redefinitions
    (`__builtin_assume_aligned`) and silently linked an old `Framework.lib`. Deleting the PCH
    fixes it. Also: `-m:4`+ can ICE on `DayScene`; retry at `-m:2` or `/m:1`.
16. **Orbit camera profile overwrote the authored transform** — call `SetActiveProfile(FreeFly)`
    before `AttachCamera`.
17. **Camera mouse look** — Y inverted (wanted), X inverted (not wanted); X was reverted.

### Rendering
18. **`RenderMesh::Draw` has no generic texture loop.** A declared-but-unbound SRV returned 0, so
    the water ignored the solver entirely until slot **t23** got its own branch.
19. **Water writing GBuffer depth** left SSR nothing to trace against → `DrawPassMask`.
20. **Camera-height-dependent thickness** caused dark patches that slid with the camera.
21. **`displacementScale = 12`** turned every real feature into a crater; now 1.0.
22. **Nearest-texel shading with bilinear geometry** caused the flashing surface (§9.5).
23. **Surface texture contract**: R must be a *delta*; slopes are per-texel *differences*; wall
    columns must report the water plane.
24. **Trapped air read as missing water** (W-02). The column integral treats air under the surface
    as a lower surface; once α was exact, the air a plunge leaves beside a floating ball drew a
    1.7–3 cm moat. W-02 counted deep air as volume; W-29 replaced that with `CS_FluidAirRise3D`,
    because the counted air froze into fixed bumps after every splash (§6.3, §7).
25. **The surface kernel did 9× its work.** Each tent tap recomputed a column (and its inpainting
    walks next to a body). A groupshared tile computes each column once (§7.1).

### Self-test
26. **The isotropy annulus sat 9 cm off the impact in Z.** `uint(2.25f / 0.09f)` is 24, not 25,
    so the −Z and +Z halves sampled the wave at 0.56 m and 0.44 m. The quadrant index is
    `(dx > 0) + 2 (dz > 0)`, so the "axis" gate really compared −Z with +Z, and its 10.7 mm
    "operator-split anisotropy" band was this bug; centred, both halves agree within 0.6 mm.

### Body coupling
24. **Volume-only coupling produces no waves.** The body must be a solid in the pressure solve
    *and* a momentum source; either alone fails.
25. **Uniform global redistribute killed waves.** Returning removed volume as an even elevation
    rise over every column low-pass-filtered the surface — any crest or trough became a flat
    offset.
26. **Synthetic sin/cos surface stir** (`forcingAmplitude = 1.0`) drowned the physics in a
    synthetic pattern. This is literally why the water looked like rolling sine waves. Now 0.0.
27. **`damping = 0.6`** removed almost all of a wave's energy within a second. Now 0.05.
28. **Tunnelling.** Above `cellSize/dt` the body jumps over water it never touches → substepping.
29. **`surfaceLevel` literal overriding the derived fill** → a reset re-seeded at 96% instead of
    78.8%.

## 15. Tradeoffs and known limitations

### Resolution vs cost
0.09 m cells over a 100 × 22 × 50 grid is 110,000 voxels. A 0.25 m ball spans only ~5 cells, so
the cavity cannot be resolved finer than that and the wavefront reads slightly stair-stepped.
Going to 0.045 m (200 × 44 × 100 ≈ 880k voxels) is the real cure for splash detail at roughly
**8× the sim cost**. Not taken yet.

### SOR iterations vs propagation
60 sweeps over a 100-cell domain propagate a disturbance ~60 cells, which is enough. Fewer
sweeps localise it. A heightfield wave solver (`c = √(g·h)`) was recommended as an alternative
for the *visible* surface but rejected: it cannot do a 3D cavity collapse, and it changes the
semantics from "render the conserved volume" to "render a separate 2D surface".

### Surface tension: deferred, deliberately
All three parties agreed it is **physically meaningless at 9 cm cells**. Capillary length for
water at 20 °C is ≈ 2.7 mm, i.e. **33× below the cell size**. Any surface-tension term at this
resolution would be a visual fudge, not physics.

### Buoyancy: bespoke, not Jolt
The body uses an analytic Archimedes integrator (`a_net = g(submerged/ρ_rel − 1)`) rather than
Jolt. Jolt is present in the engine and was the stated intention, but coupling a rigid body to a
VOF volume needs a custom submerged-volume query, and the analytic sphere gives that exactly. The
integrator is honest about being a sphere model: it has no rotation, no added-mass tensor, and no
contact with the pool steps. Its water line is sampled from the simulated surface (§8.1), so it is
coupled to the solver in both directions, but only through that level — the body does not displace
α out of the cells it occupies (W-07, still open).

### "Everything from JSON": partial
The pool layout is JSON and authoritative (`waterPlaneY`, `freeboard`, step AABBs, grid height
derived from it). The ~90 water tunables are still C++ defaults in WaterTunables.h — they are
*overridable live from the GUI* but not loaded from a file. This is the largest outstanding gap
against the "nothing hardcoded" requirement.

### Fixed vs real timestep
Default is **real delta** (`fixedTimeStep = false`) so the water runs in real time; `maxDeltaTime`
clamps pathological frames to 1/30 s (half the explicit viscous von Neumann bound
`h²/(6ν) = 0.0675 s`). A deterministic fixed step (1/60) exists and was used to exercise the
substep path reproducibly.

### Substep cost
Up to 12 substeps per frame means up to 12× the pressure-solve cost, only while the body moves
fast. The wall-mask work was made affordable (bounding-box scan + footprint skip) to keep this
viable.

### Generated assets are not committed
`.glb` files are gitignored. Regeneration needs Blender for the yard and plain Python for the
ball and normal map.

### Vulkan fluid selftest harness
`--fluid-selftest` reports `SKIP: API=vulkan has no volumetric compute storage` — a pre-existing
capability probe in the test harness, not the solver. The **scene itself runs correctly on
Vulkan** with all compute pipelines created and identical measured results.

### Dead code
`CS_FluidSphere3D.hlsl`, `InjectSphere` and its `Removed` buffer are retained but no longer called
by the frame loop (the wall mask handles the body footprint). They are kept as a diagnostic path
and would be removed in a cleanup pass.

### Stale comment
`WaterGpuParams` carries a comment saying "Fifteen float4 groups"; the struct now has **24**.
Worth fixing in a doc pass.

## 17. Working protocol

Every design decision in this work was cross-checked against **two independent local models**
(`glm-glm` on the dual NVIDIA Sparks, `qwen-qwen` on the RTX 5090), and disagreements were
resolved explicitly rather than averaged.

Where they disagreed:

- **Probing texel (0,0)** — GLM proposed it; Qwen pointed out it is a wall column and therefore
  useless as a surface probe.
- **Setting α = 1 in swept cells** — GLM initially said this was correct; Qwen corrected that the
  overlapped volume must be *removed*, not set, or the pool level rises unrealistically.
- **Blockiness of the wave surface** — GLM ranked a tent filter first; Qwen argued vertex density
  and hardware interpolation first, because the storage texture is not filterable. The
  implemented solution used both: manual bilinear reconstruction in *both* stages plus a denser
  water mesh.
- **Tunnelling diagnostics** — both converged independently on tunnelling as the primary cause of
  "the ball passes through with no splash", and both recommended substepping over swept-volume
  stamping alone. Qwen supplied the concrete threshold `v_max = h/dt = 5.4 m/s`.

Where they agreed, the answer was implemented without further debate: the missing term was
`u·n = u_body·n`; the uniform redistribute pass was actively suppressing waves; the multiplicative
volume correction was dead on arrival; mass should be derived from density and radius rather than
treated as independent; a reset must clear momentum, not just position.
